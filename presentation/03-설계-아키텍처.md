# 03-1. 설계 — 아키텍처 (시스템·ERD·프론트)

## 🖥 슬라이드에 넣을 것
- [다이어그램: 브라우저(Vue SPA) ↔ Nginx ↔ Django ↔ (DB + 외부 AI)]
- [다이어그램: ERD 큰 그림 — 사용자·제품·게시글이 선으로 연결]
- 한 줄 숫자: **API 23개 · 백엔드 테스트 63개 · 화면 약 13개**
- 프론트: **Vue SPA · 라우터 가드 · 자동 토큰 갱신 · 디자인 토큰**

## 🎤 이렇게 말하세요
"시스템은 역할을 딱 나눴습니다. 화면을 그리는 **Vue**, 입구에서 교통정리하는 문지기 **Nginx**, 실제 일을 처리하는 두뇌 **Django**, 데이터를 보관하는 창고 **데이터베이스**, 그리고 대화를 이해하는 **외부 AI**. 이렇게 나눠 두면 문제가 생겨도 어디가 원인인지 빨리 찾습니다.

데이터 저장 설계도(ERD)는 어렵게 보실 것 없이 **엑셀 시트를 여러 장으로 나눠 둔 것**이라고 보시면 됩니다. 사용자 시트, 제품 시트, 게시글 시트… 그리고 선들은 '이 사용자가 찜한 제품은 저 제품 시트의 몇 번 줄'처럼 **표끼리 잇는 끈**입니다. 나눠 두면 정보가 꼬이지 않아요. 이걸 합쳐 화면과 서버가 주고받는 통로(API)를 **23개** 만들고, 백엔드는 **63개 테스트**로 검증했습니다.

화면은 **Vue로 만든 SPA**입니다. 페이지를 통째로 새로 받지 않고 필요한 부분만 바꿔 끼워 새로고침 없이 매끄럽게 움직여요. 로그인 흐름은 두 장치로 매끄럽게 했는데, 첫째 **라우터 가드** — 로그인 안 한 사람이 마이페이지에 오면 막고 로그인으로 돌려보냅니다. 둘째 **자동 토큰 갱신** — 출입증이 만료돼도 조용히 새로 받아 하던 일을 이어 갑니다. 디자인은 색·간격·글꼴을 변수로 묶은 **디자인 토큰**으로 통일해, 한 곳만 바꿔도 전체 톤이 같이 바뀝니다."

## 💡 왜 이 선택?
**Django REST + Vue SPA (명세가 둘 중 택1 요구)**

| 비교 | (A) Django + 템플릿 | (B) Django REST + **Vue SPA ✅** |
|------|---------------------|-------------------------------|
| 화면 반응성 | 페이지마다 새로고침 | 새로고침 없이 매끄럽게 |
| 챗봇 같은 동적 화면 | 번거로움 | Vue가 강점 |
| 프론트/백 분리 | 한 덩어리 | 명확히 분리 → 분업·테스트 쉬움 |

→ 챗봇이 핵심이라 메시지가 새로고침 없이 오가는 **SPA**가 결정적이었습니다. 두 기술을 다 다뤄야 하는 부담은 감수했습니다.

**디자인 토큰 vs 인라인 스타일**: 인라인은 같은 "크림색"이 화면마다 미묘하게 달라지고 색 하나 바꾸려면 수십 군데를 고쳐야 합니다. 토큰은 `base.css` 한 곳만 바꾸면 전체가 바뀌어 일관성·유지보수를 둘 다 잡습니다. 아이콘도 기기마다 모양이 다른 이모지 대신 **커스텀 라인 아이콘**으로 톤을 통일했습니다.

## ❓ 예상 질문 & 답변
**Q. ERD를 굳이 표를 여러 개로 나눈 이유는?**
A. 한 표에 다 넣으면 정보가 중복되고 꼬입니다. 사용자·제품·게시글을 나누고 끈으로 이으면, 같은 제품을 여러 사람이 찜하거나 여러 글에 태그해도 깔끔합니다.

**Q. 토큰이 동시에 여러 요청에서 만료되면 중복 갱신되지 않나요?**
A. 갱신은 딱 한 번만 하도록 묶어, 중복 갱신이나 잘못된 로그아웃을 막았습니다.

**Q. 화면이 몇 개인가요?**
A. 홈·상담(추천/진단)·둘러보기·커뮤니티(목록·작성·상세·수정)·마이페이지·로그인 등 약 13개로, 명세 NF1304(5개 이상)를 충족합니다.

> Vue 3 + Pinia + Vue Router + Vite · 디자인 시스템 "Botanical Editorial".
