# 04-2. 회고 — 협업 (Git 전략)
> 발표 파트 · beautalk · 권장 0.5분

## 🖥 슬라이드에 넣을 것
- 한 줄 핵심: **여러 명이 같은 코드를 동시에 고쳐도 충돌 없이 합치는 규칙**
- 흐름: `develop` → 기능 브랜치 → PR(동료 리뷰) → 머지
- 안전장치: `develop` 직접 푸시 잠금 → 반드시 리뷰
- [캡처: GitLab/GitHub 커밋 내역 스크린샷] *(명세 1.6 요구)*

## 🎤 이렇게 말하세요
"여러 명이 하나의 코드를 동시에 고치면 같은 줄을 다르게 바꿔 부딪히는 '충돌'이 납니다. 심하면 누군가의 작업이 통째로 날아가죠. 그래서 각자 '복사본 가지'에서 작업하고, 다 되면 한 곳으로 안전하게 합쳤습니다.

항상 동작하는 기본 줄기 `develop`이 있고, 기능마다 가지를 따로 쳐서 개발합니다. 다 되면 '합쳐 주세요' 요청(PR)을 올리고, 동료가 검토한 뒤에야 `develop`에 합쳐집니다. `develop`에는 직접 못 밀어 넣게 잠가, 모든 변경이 반드시 리뷰를 거치게 했습니다. 덕분에 백엔드·프론트가 서로 기다리지 않고 동시에 개발했습니다."

## 💡 왜 이 선택?
| 선택지 | 방식 | 우리에게는 |
|---|---|---|
| main 직접 푸시 | 가지 없이 바로 밀어 넣음 | ❌ 충돌·사고, 리뷰 없음 |
| GitFlow | 가지 종류 많은 정식 릴리스 | ❌ 소규모엔 과중 |
| **GitHub Flow (채택)** | `develop` + 기능 가지 + PR | ✅ 가볍지만 리뷰·보호 확실 |

> 명세 **NF1301(Git 활용)** 충족: 브랜치 전략 + 한글 커밋 규칙·PR 템플릿·브랜치 보호.

## ❓ 예상 질문 & 답변
**Q. 충돌이 실제로 난 적 있나요?**
A. 네. 오래 떨어져 있던 배포 준비 브랜치가 그사이 바뀐 `develop`과 같은 설정 파일을 다르게 수정해 충돌이 났습니다. `develop`을 다시 끌어와 옳은 최신값을 직접 판단해 정리했고, 이후엔 자주 동기화해 충돌을 작게 유지했습니다.

**Q. 리뷰가 개발 속도를 늦추지 않나요?**
A. 오히려 버그를 머지 전에 걸러 재작업이 줄었고, API 계약을 먼저 합의해 병렬 개발했기에 전체 속도는 더 빨랐습니다.
