# 03-5. 설계 — 배포
> 발표 파트 · beautalk · 권장 1분

## 🖥 슬라이드에 넣을 것
- **배포 = "내 노트북에서만 되던 걸, 인터넷 누구나 접속하게"**
- [다이어그램: EC2 한 대(메모리 1GB) 안에 Docker 상자 3개 — db · backend · nginx. 맨 앞 Nginx가 교통정리]
- **HTTPS 자물쇠** 적용 (무료 인증서 Let's Encrypt)
- 결과: **`https://beautalk.site` 실서비스 가동** · 명세 F1305(심화) 충족

## 🎤 이렇게 말하세요
"배포는, 지금까지 제 노트북이 꺼지면 아무도 못 쓰던 걸 인터넷에 항상 켜진 서버에 올려 누구나 `beautalk.site`로 접속하게 만드는 작업입니다.

AWS에서 작은 서버 한 대(메모리 딱 1기가)를 빌렸어요. 이 한 대 안에 **Docker로 세 개의 상자**를 띄웠습니다. 데이터 창고(DB), 계산·AI 추천을 만드는 두뇌(백엔드), 맨 앞에서 손님을 맞는 안내데스크(Nginx)입니다. 안내데스크가 핵심인데, 들어오는 요청을 받아 '이건 화면, 이건 백엔드'로 **교통정리**합니다.

주소창의 **자물쇠(HTTPS)**도 적용했습니다. 카카오·구글 로그인 정보가 암호화 없이 오가면 가로채질 수 있어, 무료 인증서로 막았습니다. 결과적으로 누구나 접속하는 진짜 서비스가 됐고, 명세의 배포 심화 항목도 충족했습니다."

## 💡 왜 이 선택?
핵심 제약은 **"메모리 1GB 작은 서버 한 대"** 와 **"비용·학습 부담 최소화"** 였습니다.

| 선택지 | 장점 | 단점 | 결정 |
|---|---|---|---|
| **단일 EC2 + Docker (채택)** | 저렴, 구성 한눈에, 학습 가치 | 서버 죽으면 전체 중단 | ✅ 비용·학습·규모 최적 |
| 관리형 PaaS | 운영 편함 | 비용↑, pgvector 특수 설정 어려움 | ❌ |
| 분리 배포(여러 대) | 확장성↑ | 비용·관리 복잡 | ❌ 과함 |

- 메모리 1GB에 맞춰 상자마다 한도를 나눴습니다(nginx 64MB + backend 450MB + db 256MB).
- **프론트 빌드는 EC2에서 안 했습니다.** 빌드는 메모리를 크게 먹어 작은 서버가 멈출 위험 → 개발자 PC에서 미리 빌드해 **결과물만 올려** 메모리를 백엔드·DB가 쓰게 아꼈습니다.

## ❓ 예상 질문 & 답변
**Q. 서버 한 대면 죽으면 다 멈추는 것 아닌가요?**
맞습니다, 단일 서버의 단점입니다. 다만 데이터 300건·트래픽이 작아 한 대로 알뜰히 운영하는 이점이 더 컸습니다. 규모가 커지면 분리 배포로 확장 가능한 구조입니다. (→ 04 회고 / 아쉬운 점)

**Q. HTTPS 인증서가 무료인데 괜찮나요?**
Let's Encrypt 공인 기관 무료 발급이고 certbot으로 자동 갱신됩니다. 보안 수준은 유료와 동일합니다.

**Q. 민감 정보 관리는?**
키는 코드에 안 넣고 `.env`로 서버에만 주입 → GitHub 시크릿 0건.
