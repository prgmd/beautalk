# 인증과 보안

> 발표 파트 · beautalk · 권장 1분

## 🖥 슬라이드에 넣을 것

- **비밀번호는 우리가 안 받습니다** — 카카오·구글에 신원 확인 위임 (OAuth)
- **디지털 출입증(JWT)** — 위조하면 서명이 깨져 바로 들통
- **git에 비밀 키 0건** — 명세 NF1302 충족
- [캡처: `git ls-files | grep env` 결과 — 추적되는 env 파일은 주소 한 줄(`VITE_API_BASE=...`)뿐]
- [다이어그램: 카카오로 로그인 클릭 → 카카오가 본인 확인 → 우리 서버가 출입증(JWT) 발급 → 이후 요청마다 출입증 제시]

## 🎤 이렇게 말하세요

저희는 사용자의 비밀번호를 아예 받지 않습니다. 대신 카카오나 구글에 "이 사람 맞다"고 대신 확인받는 방식, OAuth를 씁니다. 가장 안전한 비밀번호는 우리가 아예 갖고 있지 않은 비밀번호니까요. 보관 안 하는 정보는 샐 수도 없습니다.

로그인이 끝나면 위조 못 하게 서명된 디지털 출입증, JWT를 발급합니다. 누가 손대면 서명이 깨져서 바로 들통납니다. 이 출입증을 매번 내밀면 입장이 되는 구조입니다.

그리고 가장 자신 있게 말씀드릴 수 있는 부분인데요. 저희 git 저장소에는 비밀 키가 단 한 줄도 없습니다. 직접 확인하실 수 있게 명령어 한 줄을 슬라이드에 띄웠는데, 추적되는 건 누구나 봐도 되는 API 주소 한 줄뿐입니다. 진짜 비밀값은 서버에만 있는 `.env` 파일에 두고, 그 파일은 git에 아예 안 올라가게 막아 뒀습니다. 명세서 NF1302 요구사항을 그대로 충족한 부분입니다.

## 💡 왜 이 선택?

**(1) 자체 회원가입 vs 소셜 OAuth**

| 방식 | 우리가 비밀번호를 | 위험 |
|------|------------------|------|
| 자체 회원가입 | 직접 보관함 | DB가 털리면 비밀번호 유출, 책임도 우리 몫 |
| **소셜 OAuth (선택)** | 아예 안 들고 있음 | 보관 안 하니 샐 수도 없음 |

**(2) 출입증 보관 위치 — localStorage vs HttpOnly 쿠키**

| 보관 위치 | 악성 스크립트(XSS)가 훔칠 수 있나 |
|-----------|----------------------------------|
| localStorage | 털림 (자바스크립트가 그대로 읽음) |
| **메모리 (짧은 출입증, 선택)** | 노출 표면이 작음 |
| **HttpOnly 쿠키 (긴 출입증, 선택)** | 자바스크립트가 아예 못 읽음 |

→ 출입증을 둘로 나눠, 자주 쓰는 짧은 표(30분)는 메모리에, 재발급용 긴 표(7일)는 자바스크립트가 못 읽는 쿠키에 보관합니다.

## ❓ 예상 질문 & 답변

**Q. 그럼 보안 완벽한가요?**
완벽하다고 말씀드리지 않겠습니다. 핵심 방어막(OAuth, 출입증 분리 보관, 소유권 검사, 키 분리)은 갖췄지만, 보완 여지도 솔직히 남아 있습니다. 세션·CSRF 쿠키에도 Secure 적용, HSTS(항상 HTTPS만 쓰도록 강제) 추가, CORS 허용 주소를 코드 고정값이 아니라 운영 환경변수로 분리하는 것이 다음 단계입니다.

**Q. 출입증이 30분이면 30분마다 다시 로그인하나요?**
아닙니다. 짧은 출입증이 만료되면 프론트가 알아서 긴 출입증으로 새 출입증을 받아옵니다. 사용자는 눈치도 못 챕니다.

**Q. 남의 데이터를 번호만 바꿔서 보는 공격(IDOR)은요?**
모든 데이터 조회를 "지금 로그인한 사람 것"으로 범위를 좁혀서 처리합니다. 남의 번호를 넣어도 본인 조건에 막혀 아무것도 안 잡힙니다.
