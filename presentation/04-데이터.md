# 데이터 확보와 정제
> 발표 파트 · beautalk · 권장 1분

## 🖥 슬라이드에 넣을 것
- 한 줄 핵심: **양질의 데이터가 추천의 토대**
- 4단계 흐름: 수집(크롤링) → AI 요약 → 정제 → fixture
- 숫자: 올리브영 제품 **306종** 확보 (크롤링 → 중복 제거 → 요약·임베딩 99.7%)
- [다이어그램: 올리브영 크롤링 → AI 요약 → 정제 → products_seed.json → loaddata]

## 🎤 이렇게 말하세요
"추천 서비스가 동작하려면 먼저 제품 데이터가 있어야 합니다. 저희는 이 데이터를 네 단계로 만들었습니다.

첫째, 수집입니다. '크롤링'이라고 하는데, 웹사이트를 자동으로 돌아다니며 필요한 정보를 긁어오는 걸 말합니다. 올리브영의 스킨케어·클렌징·선케어·메이크업 등에서 제품과 후기를 모아, 중복을 정리한 뒤 최종 **306종**을 확보했습니다.

둘째, AI 가공입니다. 한 제품에 후기가 수천 개씩 달리기도 하는데, 이걸 그대로 쓰면 너무 무겁고 광고 같은 잡음도 섞여 있습니다. 그래서 인공지능으로 후기를 한두 문장 핵심 요약으로 바꾸고, '지성 피부에 좋아요', '건성에 좋아요' 같은 피부타입별 만족도도 정리했습니다.

셋째, 정제입니다. 같은 제품이 여러 주소로 중복 들어온 걸 제품 고유 번호로 묶어 정리하고, 비어 있던 요약을 채우고, 가격과 카테고리가 맞는지 점검하는 **정제 파이프라인**을 만들었습니다.

넷째, fixture화입니다. fixture는 데이터베이스를 한 번에 채워 넣는 초기 데이터 파일인데요, 정리한 결과를 파일로 저장해 명령어 한 줄로 누구나 똑같은 데이터를 다시 만들 수 있게 했습니다.

정리하면, 잘 가공한 데이터가 추천 품질을 떠받칩니다. 양질의 데이터가 곧 추천의 토대입니다."

## 💡 왜 이 선택?
**데이터를 어디서 — 공개 API vs 직접 크롤링**

| 선택지 | 단점 | 결정 |
|---|---|---|
| 공개 API | 화장품·리뷰에 딱 맞는 데이터를 주는 곳이 마땅치 않음 | ✗ |
| **직접 크롤링** | 손이 더 가지만 화장품에 맞는 제품·리뷰를 직접 확보 | ✓ |

**리뷰를 어떻게 — 원문 vs AI 요약**

| 선택지 | 단점 | 결정 |
|---|---|---|
| 원문 그대로 | 양이 많고 잡음 섞여 추천 근거로 무거움 | ✗ |
| **AI 요약** | 요약 단계가 추가되지만 가볍고 깔끔한 추천 근거 | ✓ |

> 명세 **NF1303** 충족: 올리브영 직접 크롤링으로 데이터 자체 확보(306종, 요약·임베딩 99.7%), `products_seed.json`·`board_seed.json`을 `loaddata` 한 줄로 적재 → 누구나 동일 환경 재현.

## ❓ 예상 질문 & 답변
**Q. 중복은 어떻게 정리했나요?**
A. 같은 제품이 카테고리마다 다른 주소로 중복 수집될 수 있어, 제품 고유 번호(goodsNo)로 묶어 대표 1건만 남기는 정제를 적용했습니다.

**Q. 크롤링은 함부로 해도 괜찮나요?**
A. 수집 전에 올리브영의 robots.txt(자동 수집 허용 규칙)와 이용 조건을 확인하고, 허용 범위 안에서만 모았습니다.

**Q. 데이터 품질이 추천에 그렇게 중요한가요?**
A. 네. 추천이 이상하다는 제보의 진짜 원인이 알고리즘이 아니라 데이터 품질이었던 경험이 있어, 좋은 추천은 좋은 데이터에서 시작된다는 걸 분명히 확인했습니다.

**Q. 비어 있던 요약은 어떻게 채웠나요? (★ 길을 튼 이야기)**
A. 처음엔 올리브영 페이지를 다시 크롤링(Selenium)해 요약을 긁어오려 했는데, 알고 보니 **선크림·기획세트엔 올영이 애초에 AI 요약을 안 달아** 재크롤링으로는 못 채웠습니다. 그래서 발상을 틀어, **리뷰를 가볍게(requests API) 가져와 LLM이 직접 한두 문장으로 요약**하게 했습니다. 무거운 Selenium 없이, 챗봇에 쓰던 LLM 호출을 그대로 재사용해 요약 커버리지를 99.7%까지 끌어올렸습니다. **"데이터가 알려주는 대로 길을 바꾼"** 사례입니다.
