> 발표 파트 · beautalk · 권장 1분

## 🖥 슬라이드에 넣을 것
- 제목: **기획 — 무엇을 꼭 하고, 무엇을 포기했나**
- 우선순위 표 (3줄): **꼭 한다** 챗봇 추천·커뮤니티·배포 / **하면 좋다** 추천 기록·제품 상세 / **포기** 추천 피드백·대시보드 차트
- [다이어그램: 시스템 아키텍처 — 브라우저(Vue) ↔ Nginx ↔ Django ↔ (DB + 외부 AI)]
- [다이어그램: ERD 큰 그림 — 사용자·제품·게시글 표가 선으로 연결된 모습]
- 한 줄 숫자: **API 23개 · 백엔드 테스트 63개**

## 🎤 이렇게 말하세요
"기획에서 가장 먼저 한 건 **'무엇을 안 할지'를 정하는 일**이었습니다. 정해진 기간에 다 만들 순 없으니까요. 챗봇 추천, 커뮤니티, 실제 배포는 **반드시 한다**로 두고, 추천에 좋아요·별로예요를 남기는 피드백 기능이나 보기 좋은 대시보드 차트는 **과감히 포기**했습니다. 핵심인 '추천'에 시간을 몰아주기 위해서였죠.

다음은 시스템을 어떤 부품으로 나눌지입니다. 화면 그리는 **Vue**, 입구에서 교통정리하는 문지기 **Nginx**, 실제 일을 처리하는 두뇌 **Django**, 데이터를 보관하는 창고 **데이터베이스**, 그리고 대화를 이해하는 **외부 AI**. 이렇게 역할을 딱 나눠서, 문제가 생겨도 어디가 원인인지 빨리 찾을 수 있게 했습니다.

그리고 이 화살표(ERD)는 데이터를 어떻게 저장했는지 보여주는 **설계도**입니다. 어렵게 생각하실 것 없이, **엑셀 시트를 여러 장으로 나눠 둔 것**이라고 보시면 됩니다. 사용자 시트, 제품 시트, 게시글 시트… 그리고 이 선들은 '이 사용자가 찜한 제품은 저 제품 시트의 몇 번 줄'처럼 **표끼리 연결하는 끈**입니다. 이렇게 나눠 두면 정보가 꼬이지 않고 깔끔하게 관리됩니다.

이 모든 걸 합쳐 화면과 서버가 주고받는 통로(API)를 **23개** 만들었고, 백엔드는 **63개의 테스트**로 검증했습니다."

## 💡 왜 이 선택? — 왜 Django REST + Vue SPA인가
명세서는 두 방식 중 하나를 고르라고 했습니다.

| 비교 | (A) Django + 템플릿 | (B) Django REST + **Vue SPA ✅** |
|------|---------------------|-------------------------------|
| 화면 반응성 | 페이지마다 새로고침 | 새로고침 없이 매끄럽게 |
| 챗봇 같은 동적 화면 | 만들기 번거로움 | Vue가 강점 |
| 프론트/백 분리 | 한 덩어리, 분업 어려움 | 명확히 분리 → 분업·테스트 쉬움 |
| 초기 부담 | 단순 | 두 기술 다뤄야 해 부담 ↑ |

- **고른 이유:** 챗봇이 핵심 경험이라, 메시지가 새로고침 없이 오가는 **SPA 방식**이 사용자 경험에 결정적이었습니다. (SPA = 페이지 전체를 다시 안 불러오고 필요한 부분만 바꿔 그려 앱처럼 매끄러운 방식)
- **감수한 단점:** 두 기술을 다 다뤄야 하고, 프론트·백을 잇는 인증·연결 작업이 더 듭니다. 핵심 기능 품질을 위해 감수할 가치가 있다고 봤습니다.

## ❓ 예상 질문 & 답변
**Q. 포기한 기능들은 영영 안 하나요?**
A. 의도적으로 범위에서 뺀 것입니다. 피드백은 데이터가 충분히 쌓여야 의미가 있고, 대시보드는 핵심 가치인 '추천'과 거리가 있어 우선순위에서 내렸습니다.

**Q. ERD를 굳이 표를 여러 개로 나눈 이유가 있나요?**
A. 한 표에 다 넣으면 정보가 중복되고 꼬입니다. 사용자·제품·게시글을 따로 나누고 끈(연결)으로 이으면, 같은 제품을 여러 사람이 찜하거나 여러 글에 태그해도 깔끔하게 관리됩니다.

**Q. 외부 AI는 직접 만든 건가요?**
A. 아니요, 직접 만들기 어려운 자연어 이해는 외부 AI(SSAFY가 제공하는 LLM)를 빌려 쓰고, 저희는 그 결과를 추천에 맞게 가공하는 역할을 했습니다.
