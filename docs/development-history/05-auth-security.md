# 05. 인증과 보안

## ① 한 줄 요약

비밀번호를 직접 받지 않는 **카카오·구글 소셜 로그인**으로 사용자를 확인하고, 로그인 후에는 **위조 못 하는 디지털 출입증(토큰)**으로 출입을 관리하며, 남의 데이터를 못 건드리게 막고, 비밀 열쇠(키)는 코드와 분리해 단 한 건도 git에 올리지 않은 단계입니다.

---

## ② 무엇을 했나 (쉽게)

이 단계에서 한 일을 한 줄로 늘어놓으면 이렇습니다.

> 소셜 로그인 → 디지털 출입증(JWT) 발급·자동 갱신 → 권한·소유권 검사 → 비밀 열쇠 분리 → 과도한 사용(남용) 방지

용어부터 쉽게 풀어 두겠습니다.

- **OAuth** = 비밀번호를 우리한테 알려주는 대신, **카카오/구글에 "이 사람 맞다"고 대신 확인받는 방식**입니다.
- **JWT** = **위조 못 하게 서명된 디지털 출입증**. 서버가 발급하고, 누가 손대면 서명이 깨져 바로 들통납니다.
- **소유권 검사** = "이 데이터, 정말 네 거 맞아?"를 매번 확인하는 절차입니다.

### 로그인 한 번의 흐름

사용자 눈에는 버튼 한 번이지만, 뒤에서는 이런 일이 일어납니다.

```
[사용자가 "카카오로 로그인" 클릭]
        │
        ▼
[카카오가 본인 확인]  ← 비밀번호는 카카오만 알고, 우리는 모릅니다
        │
        ▼
[우리 서버가 "이 사람 맞네" 확인 후 → 디지털 출입증(JWT) 발급]
        │
        ▼
[이후 모든 요청에 출입증을 내밀며 입장]
```

즉, **우리 서버는 비밀번호를 단 한 글자도 저장하지 않습니다.** 본인 확인은 카카오·구글에 맡기고, 우리는 "확인됐다"는 결과만 받아 출입증을 만들어 줍니다.

### 사용자를 무엇으로 구별하나

이메일이 아니라 **카카오/구글이 발급한 고유 번호(provider_id)**로 사람을 구별합니다. 예를 들어 같은 이메일을 카카오 계정과 구글 계정이 함께 쓰더라도 서로 섞이지 않습니다. 그리고 새로 가입하려는 이메일을 이미 다른 계정이 쓰고 있으면, 조용히 합쳐 버리지 않고 **명시적으로 "이미 사용 중" 오류**를 돌려줍니다(계정 충돌·탈취 방지).

---

## ③ 왜 이렇게 했나 — 선택지 비교

보안 설계는 대부분 "둘 중 무엇이 덜 위험한가"의 선택입니다. 핵심 갈림길 세 가지를 표로 정리했습니다.

### (a) 비밀번호를 직접 받을까, 소셜 로그인으로 받을까

| 방식 | 우리가 비밀번호를 | 위험 |
|------|------------------|------|
| 자체 회원가입(비밀번호 저장) | **직접 보관함** | 우리 DB가 털리면 비밀번호가 샘 → 책임도 우리 몫 |
| **소셜 OAuth (선택)** | **아예 안 들고 있음** | 보관 안 하는 정보는 샐 수도 없음 |

> 핵심: **"가장 안전한 비밀번호는 우리가 갖고 있지 않은 비밀번호"** 입니다. 본인 확인은 보안 전문 인력이 지키는 카카오·구글에 맡기는 편이 더 안전합니다.

### (b) 출입증을 어디에 보관할까 — localStorage vs HttpOnly 쿠키

> **XSS** = 공격자가 악성 자바스크립트를 페이지에 심어 브라우저 안의 정보를 훔쳐 가는 공격입니다.

| 보관 위치 | 자바스크립트가 읽을 수 있나 | XSS에 털리나 |
|-----------|----------------------------|--------------|
| localStorage | 읽을 수 있음 | **털림** (악성 스크립트가 꺼내 감) |
| **메모리 (access 토큰, 선택)** | 페이지 안에서만, 새로고침하면 사라짐 | 노출 표면이 작음 |
| **HttpOnly 쿠키 (refresh 토큰, 선택)** | **자바스크립트가 못 읽음** | 스크립트로는 못 꺼냄 |

그래서 우리는 출입증을 **둘로 나눠** 보관합니다.

- **짧은 출입증(access)** 은 브라우저 **메모리에만** 둡니다. 새로고침하면 사라지지만, 그만큼 훔쳐 갈 표면도 작습니다.
- **긴 출입증(refresh)** 은 **HttpOnly 쿠키**로 둡니다. 자바스크립트가 아예 읽을 수 없으니 악성 스크립트도 손댈 수 없습니다.

### (c) 출입증을 왜 짧은 것·긴 것으로 나눴나

| 토큰 | 수명 | 역할 |
|------|------|------|
| **access (짧은 출입증)** | **30분** | 평소 출입에 매번 내미는 표 |
| **refresh (긴 출입증)** | **7일** | access가 만료되면 새로 받아오는 "재발급권" |

수명을 하나로 합치면 곤란합니다. **짧게만 두면** 30분마다 다시 로그인해야 해서 불편하고, **길게만 두면** 한 번 새면 오래 악용됩니다. 그래서 **자주 쓰는 표는 짧게(30분), 재발급용 표는 안전한 곳에 길게(7일)** 두는 절충을 택했습니다. 더해서 재발급 때마다 **새 refresh로 교체(회전)하고 옛것은 블랙리스트(사용 금지 명단)**에 올려, 혹시 탈취된 옛 토큰이 재사용되지 못하게 막습니다.

## ④ 어떻게 작동하나

### 위조·도용 막기 — 가짜 콜백 차단(CSRF)

> **CSRF** = 사용자가 의도하지 않은 요청을 공격자가 몰래 대신 보내게 만드는 공격입니다.

로그인 시작 때 한 번만 쓰는 임의의 비밀값(`state`)을 만들어 보내고, 카카오/구글이 돌아올 때 그 값이 그대로 돌아왔는지 대조합니다. 값이 다르면 가짜 콜백으로 보고 즉시 거부합니다. 이 비밀값은 추측 불가능한 난수(`secrets.token_urlsafe`)로 만듭니다.

### 출입증 자동 갱신 — 사용자는 눈치채지 못함

access 토큰(30분)이 만료되면 사용자가 다시 로그인할 필요 없이 프론트가 알아서 처리합니다.

```
요청 → 서버가 "401 (출입증 만료)" 응답
     → 프론트가 자동으로 refresh로 새 access 받아옴
     → 방금 그 요청을 새 출입증으로 다시 시도
```

동시에 여러 요청이 한꺼번에 만료를 맞아도 **재발급은 딱 한 번만** 수행하도록 묶어 두어, 중복 갱신이나 잘못된 로그아웃을 막았습니다.

### 남의 데이터 못 건드리게 — IDOR 방어

> **IDOR** = 남의 번호표(id)를 손에 넣어 **남의 데이터를 들여다보거나 건드리는** 공격입니다.

모든 데이터 API는 우선 **로그인 필수**(`IsAuthenticated`)입니다. 거기서 한 걸음 더 나아가, 데이터를 다룰 때 **"지금 로그인한 사람의 것"으로 범위를 좁혀** 조회·수정합니다. 한 줄로 보면 이렇습니다.

```python
# 내 댓글만 골라낸다 — 남의 댓글 번호를 넣어도 걸리지 않는다
comment = Comment.objects.filter(pk=pk, user=request.user.userinfo).first()
```

남의 댓글 번호(`pk`)를 넣어도 `user=본인` 조건에 막혀 아무것도 잡히지 않습니다. 게시글 수정·삭제도 "작성자 == 나"인지 검사한 뒤에만 허용합니다.

### 비밀 열쇠 분리 — 코드에 키를 안 적는다

서비스의 모든 비밀값을 코드에서 떼어내 **환경변수(`.env` 파일)**로 분리했습니다.

| 비밀값 | 무엇인가 |
|--------|----------|
| `DJANGO_SECRET_KEY` | 서버 서명용 마스터 키 |
| `DB_PASSWORD` 등 | 데이터베이스 접속 정보 |
| 카카오·구글 `CLIENT_SECRET` | 소셜 로그인 비밀 키 |
| GMS(LLM) `API KEY` | 유료 AI 호출 키 |

코드에는 `os.environ.get('...')`처럼 **"여기 값을 넣어라"는 구멍만** 있고, 실제 값은 서버에만 있는 `.env`에서 채웁니다. `.env`는 `.gitignore`로 차단되어 git에 올라가지 않으며, 프론트엔드도 빌드에는 **공개해도 되는 주소(API URL)만** 노출합니다.

### 남용 방지 — 호출 횟수 제한(Throttling)

> **Throttling** = 짧은 시간에 너무 많이 호출하면 잠시 막아 과부하·악용을 줄이는 장치입니다.

| 대상 | 한도 | 이유 |
|------|------|------|
| 비로그인 사용자 | 20회 / 시간 | 익명 남용 차단 |
| 로그인 사용자 | 100회 / 일 | 일반 사용 보호 |
| AI 채팅(chat) | 100회 / 일 | **유료 LLM** 호출이라 별도 한도 |
| AI 추천(recommend) | 20회 / 일 | 무겁고 비싼 작업이라 더 빡빡하게 |

특히 돈이 드는 AI 기능은 일반 한도와 **따로** 두어, 한 사람이 비용을 과도하게 발생시키지 못하게 막았습니다.

### 인젝션 표면 없음

> **SQL 인젝션** = 입력값에 악성 명령을 섞어 데이터베이스를 조작하는 공격입니다.

데이터베이스 접근을 전부 Django의 **ORM(직접 SQL을 쓰지 않고 객체로 다루는 방식)**으로만 처리해, 직접 작성한 SQL이 **0건**입니다. 손으로 SQL 문자열을 짜 붙이는 곳이 없으니 SQL 인젝션이 비집고 들어올 틈도 없습니다. 또한 AI가 골라온 제품 번호는 그대로 믿지 않고 **DB로 한 번 더 검증**해, AI가 없는 제품을 지어내거나(환각) 조작한 번호를 끼워 넣어도 걸러냅니다.

## ⑤ 결과 · 배운 점

### 명세서 NF1302(API Key 관리) 충족 — 키 0건 커밋

이 단계의 가장 강한 성과는 **비밀 키를 단 한 건도 git에 올리지 않았다**는 점입니다. 누구나 다음 한 줄로 직접 확인할 수 있습니다.

```bash
git ls-files | grep env
```

추적되는 env 파일은 `frontend/.env.production` 하나뿐이며, 그 내용은 다음과 같이 **공개해도 되는 주소 한 줄**입니다.

```
VITE_API_BASE=https://beautalk.site/api/v1
```

즉 추적되는 모든 env 파일에 **비밀 키가 0건**이고, 진짜 비밀값이 든 `.env`는 `.gitignore`로 차단되어 히스토리에도 남지 않습니다. 백엔드는 `dotenv`, 프론트는 `Vite`가 환경변수를 분리해 주입합니다.

### 운영 하드닝(실제 배포를 위한 안전장치)

- **DEBUG·ALLOWED_HOSTS**를 환경변수로 분리하고 기본값을 안전한 쪽(`DEBUG=False`)으로 두었습니다. 설정을 깜빡해도 **자동으로 더 안전한 상태**가 되는 fail-safe 방식입니다.
- refresh 쿠키는 운영(HTTPS) 환경에서 **Secure**로 전송되도록 했습니다.

### 정직하게 — 앞으로 보완할 점

완벽하다고 말하지 않겠습니다. 다음은 "다음 단계"로 남겨 둔 보완 여지입니다.

- **세션/CSRF 쿠키에도 Secure** 적용, **HSTS**(브라우저가 항상 HTTPS로만 접속하게 강제) 추가
- **CORS 허용 오리진**을 코드 고정값이 아니라 운영용 환경변수로 분리

### 배운 점

보안은 한 방의 묘책이 아니라 **"여러 겹의 방어막을 겹쳐 쌓는 일"**이라는 것을 배웠습니다. 비밀번호를 아예 안 받고(OAuth), 출입증을 둘로 나눠 보관하고(메모리 + HttpOnly 쿠키), 데이터마다 주인을 확인하고(IDOR 방어), 비밀 열쇠를 코드에서 떼어내는(.env 분리) — 각각은 작은 결정이지만, 겹쳐 두면 한 겹이 뚫려도 다음 겹이 막아 줍니다.
