> 개발 이력 문서 · beautalk

# 01. 기획

## ① 한 줄 요약

"화장품 고르기가 막막하다"는 문제를, **대화하듯 물어보면 내 피부에 맞는 제품을 추천해 주는 웹앱**으로 풀기로 정한 단계입니다. 무엇을 꼭 만들고 무엇을 포기할지 우선순위를 정하고, 기능명세서·와이어프레임·유스케이스라는 세 가지 설계 밑그림을 만들었습니다.

---

## ② 무엇을 했나 (쉽게)

### 문제 정의 — "화장품, 도대체 뭘 사야 하지?"

화장품을 살 때 사람들은 보통 이런 벽에 부딪힙니다.

- **성분이 어렵다.** 성분표를 봐도 이게 내게 좋은 건지 나쁜 건지 알기 어렵습니다.
- **제형(질감)이 다양하다.** 같은 "수분 크림"이라도 토너·로션·에센스·세럼·크림처럼 형태가 제각각이라, 내 취향과 피부에 맞는 형태를 고르기 어렵습니다.
  - *제형 = 화장품의 물리적 형태/질감. 묽은 물(토너)부터 끈적한 크림까지의 정도라고 보면 됩니다.*
- **내 피부를 고려하기 어렵다.** 건성·지성·복합성·민감성 등 피부 타입과 고민(여드름·주름 등)에 따라 맞는 제품이 다른데, 이걸 일일이 따져보기가 번거롭습니다.

결국 "정보는 넘치는데, **내 상황에 맞춰 골라주는** 사람이 없다"는 게 핵심 문제였습니다.

### 타겟 사용자

- 화장품에 관심은 있지만 **성분·제형 지식이 부족한 일반 소비자**
- 리뷰를 일일이 읽고 비교하기엔 **시간과 노력이 부담스러운 사람**
- "내 피부 타입엔 뭐가 좋아?"를 **편하게 물어보고 싶은 사람**

### 핵심 아이디어 — "대화로 추천"

검색창에 키워드를 넣고 결과를 직접 비교하는 방식 대신, **챗봇에게 말을 거는 방식**을 택했습니다.

> 사용자: "지성 피부인데 끈적이지 않는 수분 제품 추천해줘"
> beautalk: (피부 프로필 + 대화 내용을 종합해) 실제 올리브영 제품 3~5개를 이유와 함께 제시

데이터는 **올리브영 제품 정보(156종)**를 크롤링해 확보했고, 여기에 AI 요약과 피부 타입별 만족도를 붙여 추천의 근거로 삼았습니다.

### 기획 산출물 — 세 가지 밑그림

집을 짓기 전 설계도를 그리듯, 개발 전에 세 가지 문서를 만들었습니다.

| 산출물 | 한 줄 설명 | 비유 |
|--------|-----------|------|
| **기능명세서 (v1.0)** | 어떤 기능을 만들지 목록과 동작을 글로 정리 | 건물의 "기능 요구사항 목록" |
| **와이어프레임** | 화면이 대략 어떻게 생겼는지 선으로 그린 밑그림 | 색·장식 없는 "흑백 평면도" |
| **유스케이스 다이어그램** | 사용자가 시스템으로 무엇을 할 수 있는지 그린 그림 | "손님이 가게에서 할 수 있는 일" 목록 |

## ③ 왜 이렇게 했나 — 기능 범위 우선순위 (MoSCoW)

한정된 기간 안에 모든 걸 다 만들 수는 없습니다. 그래서 **MoSCoW 방식**으로 우선순위를 나눴습니다.

> *MoSCoW = 기능을 "반드시(Must) / 하면 좋은(Should) / 있어도 그만(Could) / 안 함(Won't)"으로 나누는 우선순위 기법. 머리글자를 딴 이름입니다.*

| 우선순위 | 정한 것 | 결과 |
|----------|---------|------|
| **반드시 한 것 (Must)** | 대화형 추천(챗봇), 피부 프로필 온보딩, 올리브영 제품 데이터, 찜·추천 기록, 커뮤니티 게시판, 배포 | 모두 구현 |
| **하면 좋은 것 (Should)** | 추천 히스토리, 제품 상세, 제품↔게시글 태그 연결 | 구현 |
| **포기한 것 (Won't)** | **피드백(좋아요/별로예요)**, **대시보드 차트** | 의도적으로 제외 |

### 왜 피드백과 대시보드를 포기했나

- **피드백(추천에 대한 좋아요/별로예요):** 추천 품질을 높이는 데는 좋지만, 데이터가 충분히 쌓여야 의미가 있고 재추천 로직까지 붙여야 해서 기간 대비 효용이 낮다고 판단했습니다.
- **대시보드 차트:** 보기엔 좋지만 핵심 가치("추천")와는 거리가 있는 부가 기능이라, 핵심 기능의 완성도에 시간을 더 쓰기로 했습니다.

**핵심 원칙:** "넓고 얕게"보다 **"좁고 깊게"** — 추천이라는 핵심 경험을 제대로 완성하는 데 집중했습니다.

## ④ 어떻게 작동하나 — 사용자 흐름

기획 단계에서 그린 사용자 여정은 다음과 같습니다.

```
[로그인]  →  [온보딩: 내 피부 프로필 입력]  →  [챗봇과 대화]
 카카오/구글     피부 타입·고민·기피 성분          "이런 거 추천해줘"
                                                      │
                                                      ▼
                                            [추천 결과 3~5개 + 이유]
                                                      │
                            ┌─────────────────────────┼─────────────────────────┐
                            ▼                          ▼                          ▼
                       [찜하기]                  [올리브영 이동]            [커뮤니티에서 공유]
                     (마이페이지 저장)            (실제 구매 페이지)        (제품 태그한 글 작성)
```

이 흐름이 곧 와이어프레임의 화면 순서가 되고, 유스케이스 다이어그램의 "사용자가 할 수 있는 일"이 됩니다.

## ⑤ 결과 · 배운 점 — 명세서 요구사항과의 연결

프로젝트 명세서가 요구한 네 가지 큰 축은, 기획에서 정한 기능과 다음과 같이 자연스럽게 연결됩니다.

| 명세서 요구사항 | beautalk의 대응 기능 |
|-----------------|---------------------|
| **추천 서비스** | 대화형 챗봇 추천(피부 프로필 + 대화 내용 기반) |
| **외부 API 활용** | GMS(SSAFY 제공 OpenAI 프록시) LLM·임베딩으로 추천 생성, 올리브영 데이터 크롤링 |
| **커뮤니티** | 용도별 게시판(자유/Q&A·팁/세일) + 제품 태그 연결 |
| **배포** | AWS EC2 + Docker + HTTPS로 실제 도메인(beautalk.site) 서비스 |

**배운 점:** 처음부터 "무엇을 안 할지"를 분명히 정해두니, 개발 중 새 아이디어가 생겨도 흔들리지 않고 핵심에 집중할 수 있었습니다. 우선순위는 "무엇을 더할까"보다 **"무엇을 뺄까"를 정하는 일**에 가깝다는 것을 배웠습니다.
