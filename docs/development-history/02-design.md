> 개발 이력 문서 · beautalk

# 02. 설계

## ① 한 줄 요약

기획한 기능을 실제로 만들 수 있도록, **시스템을 어떤 부품으로 나누고 / 데이터를 어떤 표로 저장하고 / 화면과 서버가 어떤 약속으로 대화할지**를 그린 단계입니다. 핵심은 "프론트(화면) ↔ 서버(Django) ↔ 데이터베이스 ↔ 외부 AI"의 역할 분담과, 그 사이를 잇는 데이터 설계도(ERD)·API 규칙입니다.

---

## ② 무엇을 했나 (쉽게)

설계에서 정한 것은 크게 네 가지입니다.

1. **시스템 아키텍처** — 전체 시스템을 어떤 부품으로 쪼개고 어떻게 연결할지
2. **ERD(데이터 설계도)** — 데이터를 어떤 표들로 나눠 저장하고 표끼리 어떻게 연결할지
3. **API 설계 원칙** — 화면(프론트)과 서버가 데이터를 주고받는 규칙
4. **기술 선택** — "왜 Django REST + Vue를 골랐나"

아래에서 하나씩 풀어봅니다.

---

## ③-1. 시스템 아키텍처 — 부품을 어떻게 나눴나

> *아키텍처 = 시스템을 어떤 부품으로 나누고 서로 어떻게 연결할지 정한 큰 그림. 건물의 "구조 설계"에 해당.*

beautalk는 역할이 다른 부품들을 분리해, 각자 자기 일만 잘하도록 설계했습니다.

```
┌────────────┐    HTTPS    ┌──────────┐         ┌──────────────────┐
│  사용자     │ ─────────▶ │  Nginx   │ ──────▶ │  Django REST     │
│ (브라우저)  │            │ (문지기·  │         │  (백엔드 두뇌)    │
│  Vue SPA   │ ◀───────── │  교통정리) │ ◀────── │  비즈니스 로직     │
└────────────┘            └──────────┘         └────────┬─────────┘
                                                         │
                                    ┌────────────────────┼────────────────────┐
                                    ▼                                          ▼
                          ┌───────────────────┐                   ┌────────────────────┐
                          │ PostgreSQL +       │                   │ GMS LLM (외부 AI)   │
                          │ pgvector           │                   │ gpt-4o +           │
                          │ (데이터 저장 + 벡터)│                   │ 임베딩 모델          │
                          └───────────────────┘                   └────────────────────┘
```

각 부품의 역할:

| 부품 | 쉬운 설명 | 한 일 |
|------|-----------|-------|
| **Vue SPA (프론트)** | 사용자가 보는 화면 | 버튼·채팅창·추천 카드 등 화면 그리기 |
| **Nginx** | 건물 입구의 문지기 | 외부 요청을 받아 HTTPS 처리 후 안쪽 서버로 전달 |
| **Django REST (백엔드)** | 시스템의 두뇌 | 로그인·추천 계산·DB 조회 등 실제 일 처리 |
| **PostgreSQL + pgvector** | 데이터 창고 | 사용자·제품·게시글 저장. pgvector는 "의미가 비슷한 것"을 숫자로 찾는 검색 담당 |
| **GMS LLM (외부 AI)** | 외부에 빌린 AI 전문가 | 대화 이해·추천 문장 생성, 텍스트를 숫자(임베딩)로 변환 |

> *SPA(Single Page Application) = 페이지 전체를 새로 불러오지 않고, 필요한 부분만 바꿔 그리는 웹앱 방식. 앱처럼 매끄럽게 동작.*
> *pgvector = PostgreSQL에 "벡터(숫자 묶음) 검색" 기능을 더해주는 확장. "이 제품 설명과 의미가 비슷한 제품"을 빠르게 찾게 해줍니다.*

## ③-2. ERD — 데이터를 어떤 표로 나눴나

> *ERD = 데이터를 어떤 표들로 나눠 저장하고, 표끼리 어떻게 연결할지 그린 설계도. 표 하나하나는 엑셀 시트, 표 사이의 선은 "이 시트의 한 줄이 저 시트의 어느 줄과 연결되는지"를 뜻합니다.*

먼저 표(테이블)들이 어떻게 연결되는지 큰 그림입니다.

```
[Django User] ──1:1── [UserInfo] ──1:1── [SkinProfile]
 (로그인 계정)          (사용자 정보)        (피부 프로필)
                            │
        ┌───────────────────┼───────────────────────┬──────────────┐
        │ 1:N               │ 1:N                    │ 1:N          │ 1:N
        ▼                   ▼                        ▼              ▼
     [Like]          [InUseProduct]          [Recommendation]   [Post]
   (찜한 제품)        (사용 중 제품)         (추천 1회=배치)    (게시글)
        │                   │                        │ 1:N          │ 1:N
        │ FK                │ FK                     ▼              ▼
        ▼                   ▼               [RecommendedProduct] [Comment]
   ┌─────────────────────────────────┐    (배치 안의 추천 제품)  [PostLike]
   │           [Product]              │ ◀──── FK ─────┘
   │  (제품 306종 — 브랜드/가격/제형/  │
   │   AI요약/만족도/임베딩 벡터)       │ ◀── M:N ── [Post] (제품 태그)
   └─────────────────────────────────┘
```

### 관계를 말로 풀면

- **1:1 (일대일)** — 한 줄이 정확히 한 줄과 짝. *예: 로그인 계정 하나엔 사용자 정보 하나, 그 사용자엔 피부 프로필 하나.*
- **1:N (일대다)** — 한 줄이 여러 줄을 거느림. *예: 사용자 한 명이 찜을 여러 개 가질 수 있음.*
- **M:N (다대다)** — 양쪽 모두 여러 줄과 연결. *예: 게시글 하나에 제품 여러 개를 태그하고, 제품 하나도 여러 글에 태그될 수 있음.*
- **FK(외래키)** — "이 줄은 저 표의 몇 번 줄과 연결된다"고 가리키는 연결고리.

### 표별 핵심 정리

| 표(테이블) | 무엇을 담나 | 주요 연결 |
|-----------|------------|----------|
| **UserInfo** | 사용자 기본 정보(이메일·로그인 제공자·닉네임) | Django User와 1:1. 아래 표들의 주인 |
| **SkinProfile** | 피부 타입(건성/지성/복합성/민감성)·고민·기피 성분 | UserInfo와 1:1 |
| **Product** | 제품 306종. 브랜드·이름·가격·카테고리·AI요약·타입별 만족도·**제형(form)**·**임베딩 벡터** | 여러 표가 이 표를 가리킴 |
| **Like** | 사용자가 찜한 제품 | UserInfo(주인) + Product(대상) |
| **InUseProduct** | 사용자가 쓰는 중인 제품 | UserInfo(주인) + Product(대상) |
| **Recommendation** | 추천 1회 = 배치(부모). 한 번 추천하면 여기 1줄 | UserInfo가 소유 |
| **RecommendedProduct** | 배치에 묶인 추천 제품(자식). 추천 이유(reason) 포함 | Recommendation(부모) + Product |
| **Post** | 게시글(자유/Q&A·팁/세일) | UserInfo 소유, Product와 **M:N 태그** |
| **Comment / PostLike** | 댓글 / 게시글 좋아요 | 각각 Post에 1:N로 매달림 |

### 설계에서 신경 쓴 점

- **Product의 두 가지 검색 축:** `form`(제형, 10종 중 복수 가능)은 정확한 조건 필터용, `embedding`(1536차원 벡터)은 "의미가 비슷한 제품" 검색용입니다. 둘을 합쳐 "조건은 맞추되 의미도 비슷한" 추천을 만듭니다.
- **추천을 부모-자식 2단으로:** "추천 1회"를 부모(Recommendation), 그 안의 제품들을 자식(RecommendedProduct)으로 나눠, 한 번의 추천 묶음을 기록처럼 남깁니다. 같은 제품이 다른 날 또 추천돼도 별도 기록으로 쌓입니다.
- **게시글↔제품은 양방향:** 글에서 "이 제품 얘기예요"라고 태그하면(정참조), 반대로 제품 상세에서 "이 제품을 언급한 글 N개"도 볼 수 있습니다(역참조).

## ③-3. API 설계 원칙 — 화면과 서버의 대화 규칙

> *API = 화면(프론트)과 서버가 데이터를 주고받기로 한 약속. "이 주소로 이렇게 요청하면 이런 답을 준다"는 메뉴판.*

beautalk는 **RESTful**이라는 널리 쓰이는 규칙을 따랐습니다. 핵심은 세 가지를 분리하는 것입니다.

| 구분 | 의미 | 비유 |
|------|------|------|
| **URL = 자원(무엇)** | `/products/`, `/posts/` 처럼 "대상"을 가리킴 | 도서관의 "책장 위치" |
| **메서드 = 행위(어떻게)** | GET(조회)·POST(생성)·PATCH(수정)·DELETE(삭제) | "보다 / 새로 꽂다 / 고치다 / 빼다" |
| **상태코드 = 결과(어땠나)** | 200·201·204·400·401·403·404·502·504 | "성공 / 만듦 / 못 찾음 / 권한없음" 같은 회신 |

### 대표 엔드포인트 예시

전체 API는 `api/v1/` 접두사로 시작하고, 총 23종이며 거의 전부 로그인이 필요합니다(IsAuthenticated).

| 행위 | 메서드 + URL | 결과(성공 코드) |
|------|-------------|----------------|
| 제품 목록 보기 | `GET /api/v1/products/` | 200 |
| 챗봇에게 메시지 보내기 | `POST /api/v1/chat/` | 200 (AI 실패 시 502/504) |
| 추천 배치 생성 | `POST /api/v1/recommend/` | 201 |
| 제품 찜하기 | `POST /api/v1/likes/` | 201 |
| 찜 해제 | `DELETE /api/v1/likes/{id}/` | 204 |
| 게시글 작성 | `POST /api/v1/posts/` | 201 |
| 게시글 수정(작성자만) | `PATCH /api/v1/posts/{id}/` | 200 (남의 글이면 403) |
| 로그인 안 한 채 요청 | (인증 필요한 모든 URL) | 401 |

> *상태코드 빠른 풀이 — 200 성공 / 201 새로 만듦 / 204 성공했고 보낼 내용 없음(삭제 등) / 400 요청이 잘못됨 / 401 로그인 안 됨 / 403 권한 없음 / 404 없는 자원 / 502·504 외부 AI(GMS) 응답 실패·시간초과.*

이렇게 규칙을 통일하면, 프론트 개발자는 URL과 메서드만 보고도 "무엇을 어떻게 하는 요청인지" 바로 알 수 있어 협업이 빨라집니다.

## ③-4. 왜 Django REST + Vue SPA를 골랐나

명세서는 두 방식 중 하나를 택하라고 했습니다. 우리는 두 갈래를 비교했습니다.

| 비교 항목 | (A) Django + 템플릿 | (B) Django REST + Vue SPA ✅ 선택 |
|-----------|---------------------|----------------------------------|
| **구조** | 서버가 화면(HTML)까지 직접 그려서 보냄 | 서버는 데이터(JSON)만, 화면은 Vue가 그림 |
| **화면 반응성** | 페이지 전환마다 새로고침 | 새로고침 없이 매끄럽게(챗봇에 유리) |
| **프론트/백 분리** | 한 덩어리라 역할 구분이 흐림 | 명확히 분리 → 분업·테스트 쉬움 |
| **챗봇 같은 동적 UI** | 만들기 번거로움 | Vue가 강점 |
| **학습/구현 부담** | 비교적 단순 | 두 기술 다 다뤄야 해 초기 부담 ↑ |
| **API 재사용** | 어려움 | 같은 API를 모바일 등에 재활용 가능 |

### 우리가 (B)를 고른 이유

- **챗봇이 핵심 경험**이라, 새로고침 없이 메시지가 오가는 SPA 방식이 사용자 경험에 결정적이었습니다.
- 프론트(Vue)와 백엔드(Django)를 **명확히 분리**하면 팀이 나눠 작업하기 쉽고, 백엔드는 테스트(총 63개)로 따로 검증할 수 있습니다.
- 한 번 잘 만든 API는 **다른 화면이나 플랫폼에서도 재사용** 가능합니다.

### 트레이드오프 (감수한 단점)

- 두 기술 스택을 모두 다뤄야 해 **초기 학습·설정 비용이 큽니다.**
- 프론트와 백엔드가 따로 도니, 둘 사이 **인증(JWT)·CORS 등 연결 작업**이 추가로 필요합니다.

이 단점들은 핵심 기능(대화형 추천)의 품질을 위해 **충분히 감수할 가치가 있다**고 판단했습니다.

---

## ⑤ 결과 · 배운 점

- **부품을 분리하면 책임이 분명해진다.** 화면·두뇌·창고·외부 AI를 나누니 문제가 생겨도 어디가 원인인지 빨리 좁힐 수 있었습니다.
- **데이터 설계(ERD)가 기능의 뼈대다.** "추천을 부모-자식으로 나눈다", "게시글과 제품을 양방향으로 연결한다" 같은 결정이 이후 기능 구현의 난이도를 크게 좌우했습니다.
- **규칙을 통일하면 협업이 빨라진다.** RESTful 원칙 덕분에 프론트와 백엔드가 같은 언어로 소통할 수 있었습니다.
- 설계는 "정답"을 찾는 일이 아니라, **장단점을 알고 우리 상황에 맞게 고르는 일**이라는 점을 배웠습니다.
