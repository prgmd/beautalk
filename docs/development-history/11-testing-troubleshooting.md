# 11. 테스트와 트러블슈팅

**한 줄 요약:** 코드를 고칠 때마다 "다른 게 몰래 깨지지 않았는지"를 컴퓨터가 자동으로 검사하도록 테스트 63개를 깔아 두고, 개발 중 실제로 부딪힌 문제들을 "증상 → 원인 → 해결"로 하나씩 풀어 나간 기록입니다.

---

## ① 자동화 테스트 — 왜, 무엇을, 어디까지

### 왜 필요한가

> **자동화 테스트 = 사람이 일일이 눌러 보지 않아도, "정해진 동작이 그대로인지"를 컴퓨터가 대신 확인해 주는 검사 코드.**

소프트웨어는 한 군데를 고치면 멀쩡하던 다른 곳이 조용히 깨지는 일이 흔합니다(예: 추천 로직을 손봤더니 로그인이 망가지는 식). 사람이 매번 전부 손으로 확인하긴 어렵습니다. 그래서 "이 기능은 이렇게 동작해야 한다"를 코드로 적어 두고, 명령 한 번으로 전부 다시 검사합니다. **고치다 다른 게 깨지면 그 자리에서 빨간불**이 뜨므로, 망가진 채로 배포되는 사고를 막아 줍니다.

### 무엇을, 어떻게

- **총 63개**의 백엔드 자동화 테스트를 작성했습니다.

| 영역 | 개수 | 주로 검사하는 것 |
|------|:---:|------|
| accounts(계정) | 11 | 로그인·토큰 발급/재발급·로그아웃 같은 인증 흐름 |
| products(제품) | 8 | 제품 조회, 권한 없는 접근 차단 |
| chat(챗봇·추천) | 22 | 추천이 제대로 도는 경로(RAG)와 실패 시 대체 경로(폴백) |
| board(게시판) | 22 | 글·댓글 작성/수정/삭제(CRUD), 남의 글 못 건드리게 막기 |

- **mock(목)을 활용했습니다.**
  > **mock = 진짜 외부 호출(돈·시간이 드는 AI 서버 호출 등) 대신, 미리 정해 둔 "가짜 응답"으로 빠르게 테스트하는 기법.**

  추천 기능은 외부 LLM(대화형 AI)을 부르는데, 테스트마다 실제로 부르면 느리고(수십 초), 비용이 들고, 응답이 매번 달라져 검사가 불안정해집니다. 그래서 LLM 호출만 가짜로 바꿔 **빠르고 결과가 항상 일정한** 테스트를 만들었습니다.

### 커버 범위

- **인증 플로우** — 로그인부터 토큰 재발급까지
- **찜(좋아요)** — 등록/해제, 그리고 남의 찜은 못 건드리게 하는 **IDOR 방어**
  > **IDOR = 남의 데이터 번호만 바꿔 넣어 몰래 접근하는 보안 취약점. 이를 막는지 테스트로 확인.**
- **추천** — 정상적인 RAG 경로와, AI가 실패했을 때 동작하는 **폴백(대체) 경로** 둘 다
- **게시판 CRUD·역참조** — 글/댓글의 생성·조회·수정·삭제, 그리고 연결 관계가 올바른지

## ② 트러블슈팅 모음 (증상 → 원인 → 해결 → 배운 점)

개발하면서 실제로 막혔던 문제 8가지입니다. 비전공자도 "아, 그래서 이렇게 고쳤구나"가 느껴지도록 담백하게 정리했습니다.

### 🥇 발표에서 잘 먹히는 3대 사례

#### 1. "로션 달라"는데 "크림"을 추천한 사건

| 항목 | 내용 |
|------|------|
| **증상** | 사용자가 "지성 피부, 2~3만원대, **로션/스킨 세트**"를 요청했는데, 추천이 **토너·세럼·크림**을 내놓음. 요청한 제형(로션)을 0/3개 충족. |
| **원인** | 추천이 **의미 검색(임베딩)** 하나에만 의존했기 때문. 의미 검색은 "비슷한 분위기(지성·진정)"는 잘 찾지만, **"로션이라는 제형" "2~3만원이라는 가격 범위" 같은 딱 떨어지는 조건은 거를 수 없음.** 게다가 AI에게 후보 제품의 가격조차 안 보여 줘서, 가격을 지킬 방법이 아예 없었음. |
| **해결** | **하이브리드 검색**으로 구조를 바꿈. AI에게 넘기기 *전에* SQL로 "제형·가격 같은 조건을 먼저 걸러 내는 필터 단계"를 추가하고, 그 뒤에 의미 검색으로 정렬. (조건 필터 → 의미 유사도 → 최종 3개) |
| **배운 점** | **"비슷한 것 찾기"와 "조건 만족하는 것 찾기"는 다른 일.** 의미 검색만으로는 명시한 조건을 못 지킨다. 정형 조건은 SQL, 의미는 임베딩 — 둘을 합쳐야 한다. |

> 참고: 이 추천 실패에는 "DB에 로션 제형 데이터 자체가 거의 없었다"는 데이터 문제도 겹쳐 있었습니다(상세: `docs/recommend-failure-report.md`).

#### 2. 챗봇이 같은 질문을 빙빙 돌며 반복하던 문제

| 항목 | 내용 |
|------|------|
| **증상** | 사용자가 "성능 적당하면 됨"이라고 답해도 챗봇이 **SPF 수치를 표현만 바꿔 4번 반복** 질문. "젤/향료" 같은 **데이터에 없는 것**을 캐묻고, 심지어 "성분표를 직접 확인해 달라"며 사용자에게 일을 떠넘김. |
| **원인** | 챗봇이 **"추천 단계가 실제로 쓸 수 있는 정보가 무엇인지"를 모른 채** 대화함. 그냥 "필요한 걸 하나씩 물어봐라"라고만 시켜서, 있지도 않은 조건을 멋대로 묻고, "모름"이라는 답을 유효한 답으로 받아들이지 못해 같은 질문을 무한 반복. |
| **해결** | 챗봇의 질문을 **실제 추천 필터 축(제품군·제형·가격대·피부 고민)에만 묶고(그라운딩)**, 행동 규칙을 못 박음: ① "모름/적당히"는 유효한 답으로 인정하고 넘어가기 ② 같은 질문 재질문 금지 ③ 못 쓰는 축(향료·SPF 정확 수치)은 묻지 않기 ④ 충분하면 곧장 추천 단계(`ready`)로 직행. |
| **배운 점** | AI에게 "알아서 잘 물어봐"라고 하면 헛돈다. **실제로 쓸 수 있는 정보가 무엇인지 알려 주고(근거 부여), 하지 말아야 할 행동을 규칙으로 막아야** 대화가 목적지에 도달한다. |

#### 3. 제품 상세 모달(팝업)이 안 열리던 문제

| 항목 | 내용 |
|------|------|
| **증상** | 제품 카드를 눌러도 상세 팝업(모달)이 화면에 안 뜨거나 다른 요소에 가려짐. |
| **원인** | 앱 전체를 감싸는 영역의 **z-index/overflow 설정이 모달을 덮어 버림.** 화면에서 "누가 위에 보일지 순서"를 정하는 규칙(ID 선택자)이 모달에 건 규칙보다 우선해, 모달이 뒤로 밀려 안 보였음. |
| **해결** | 모달을 `<Teleport to="body">`로 감싸 **화면 구조의 최상위로 순간이동**시킴. 덮어 버리던 영역 바깥으로 빼내니 항상 맨 위에 표시됨. |
| **배운 점** | **z-index = 화면에서 누가 위에 보일지 정하는 순서값.** 부모 영역의 설정이 자식 팝업을 가둘 수 있어, 팝업은 아예 최상위로 빼내는 게 안전하다. |

### 그 외 트러블슈팅 (요약 카드)

#### 4. 좋아요가 새로고침하면 풀리던 문제
- **증상:** 제품에 좋아요를 눌러도 페이지를 새로고침하면 표시가 사라짐.
- **원인:** 백엔드 응답에 "이 제품을 내가 찜했는지"를 알려 주는 `is_liked` 필드가 없어, 새로고침 후 화면이 상태를 복원하지 못함.
- **해결:** 브라우저 저장소(localStorage)에 찜 상태를 보강 저장. 서버 값이 있으면 서버를 우선하고, 없을 때 저장소 값으로 복원.
- **배운 점:** 화면 상태를 유지하려면 "그 상태를 어디에 기억해 둘지"를 반드시 정해야 한다.

#### 5. JWT 토큰을 URL에 그대로 실어 나르던 초기 방식
- **증상:** 로그인 토큰(JWT)을 주소창 쿼리(`?token=...`)로 넘김.
  > **JWT = 로그인했음을 증명하는 출입증 같은 문자열.**
- **원인:** URL은 브라우저 기록·서버 로그·공유 링크에 그대로 남아 **토큰이 노출될 위험**이 큼.
- **해결:** 토큰을 URL에서 빼고, 서버에 잠깐 임시 저장한 뒤 별도 **교환 엔드포인트**로 안전하게 건넴. 재발급용 토큰은 **HttpOnly 쿠키**(자바스크립트가 못 읽는 쿠키)에 담아 탈취 위험을 낮춤.
- **배운 점:** 민감 정보는 "어디에 남는가"부터 생각해야 한다. URL에 비밀을 싣지 않는다.

#### 6. SQLite의 동시성 한계와 한글 인코딩 문제
- **증상:** 여러 요청이 몰리면 DB가 버거워하고, 한글 데이터가 깨지는 일이 있었음.
- **원인:** 초기 DB인 SQLite는 가볍지만 동시 접속 처리에 약하고 인코딩 설정도 까다로움.
- **해결:** **PostgreSQL 16**으로 전환(+벡터 검색용 `pgvector`), 인코딩을 UTF-8로 고정. 올리브영 URL이 너무 길어 잘리던 문제도 함께 발견해 `URLField` 길이를 **200 → 500**으로 늘림.
- **배운 점:** 초기엔 가벼운 도구로 시작하되, 동시성·안정성이 필요해지면 제대로 된 DB로 갈아타야 한다.

#### 7. AI 서버(GMS)가 "JSON으로만 답해" 옵션을 지원 안 하던 문제
- **증상:** 추천 결과를 프로그램이 읽으려면 정해진 형식(JSON)이어야 하는데, 쓰던 AI 서버가 "JSON 모드"를 지원하지 않음.
  > **JSON = 컴퓨터가 읽기 쉬운, 정해진 형식의 데이터 표기법.**
- **원인:** AI가 자유 형식으로 답해 버리면 프로그램이 결과를 못 알아들음.
- **해결:** 프롬프트(지시문)로 **"반드시 JSON으로만 답하라"고 강제**하고, 그래도 형식이 깨지면 **502 에러로 방어**(파싱 실패를 안전하게 처리).
- **배운 점:** 외부 AI가 항상 우리 기대대로 답하지 않는다 — 형식을 강제하고, 어긋날 때를 대비한 방어선을 둬야 한다.

#### 8. 제품 데이터 중복·가격 불일치
- **증상:** 같은 제품이 여러 주소로 중복 저장되고, 카드 가격과 실제 올리브영 가격이 다른 경우가 있었음.
- **원인:** 크롤링이 URL만 비교해 중복을 걸러, 같은 제품이 다른 주소로 중복 저장됨. 일부는 상세 수집이 중간에 멈춰 요약·가격이 비거나 어긋남.
- **해결:** 제품의 진짜 고유키(`goodsNo`)로 묶어 중복을 정리하는 **정제 파이프라인**을 만듦(중복 제거 → 리뷰 수집 → 요약 → 임베딩).
- **배운 점:** "추천이 이상하다"의 뿌리가 알고리즘이 아니라 **데이터 품질**일 수 있다. 데이터부터 들여다봐야 한다.

## 에러 처리 — 적절한 상태 코드 (명세서 F1304 연계)

명세서 **F1304(RESTful 설계·적절한 상태 코드)** 에 맞춰, 외부 AI 호출이 실패할 때도 **상황에 맞는 HTTP 상태 코드**로 정직하게 응답합니다. 예: AI 응답을 못 읽으면 **502**, 응답이 너무 느려 시간 초과면 **504**. "그냥 500 에러"로 뭉뚱그리지 않고, 무엇이 잘못됐는지 코드로 구분해 전달합니다.

## ③ 회고 — 가장 어려웠던 점 / 가장 성장한 점

- **가장 어려웠던 점:** "추천이 이상하다"는 한 가지 증상의 **진짜 원인이 여러 겹**이었다는 것입니다. 처음엔 추천 알고리즘 문제로 보였지만, 파고들수록 데이터 중복·제형 데이터 부재·프롬프트 누락·아키텍처 한계가 뒤엉켜 있었습니다. 표면 증상에 속지 않고 **원인을 끝까지 추적**하는 일이 가장 까다로웠습니다.

- **가장 성장한 점:** **"비슷한 것 찾기(의미 검색)"와 "조건을 만족하는 것 찾기(필터)"는 다른 문제**임을 몸으로 배운 것입니다. 이 깨달음이 하이브리드 추천·챗봇 그라운딩 개선으로 이어졌고, "AI에게 무엇을 보여 주고 무엇을 막을지"를 설계하는 감각이 크게 늘었습니다. 더불어 63개 테스트와 전수 코드 리뷰(`docs/review-findings.md`)를 거치며 **"고친 게 다른 걸 깨지 않았다"를 자신 있게 말할 수 있는** 안전망의 가치를 체감했습니다.
