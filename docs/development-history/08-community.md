# 08. 커뮤니티 게시판

## ① 한 줄 요약

사용자들이 **용도별로 나뉜 게시판(자유 / Q&A·팁 / 세일 정보)**에 글을 쓰고, 댓글·좋아요로 소통하며, **글에 제품을 태그**해 "추천받은 그 제품"과 "사용 후기 글"을 양방향으로 연결한 단계입니다.

---

## ② 무엇을 했나 (쉽게)

먼저 용어부터 한 줄로 풀어 두겠습니다.

- **카테고리** = 글을 주제별로 나눠 담는 칸. 여기서는 자유 / Q&A·팁 / 세일 정보 3칸입니다.
- **태그(제품 태그)** = 글에 "이 글은 OO 제품 이야기예요" 하고 꼬리표를 붙이는 것.
- **M2M(다대다)** = 글 하나에 제품 여러 개, 제품 하나에 글 여러 개가 서로 연결되는 관계.
- **정참조 / 역참조** = 같은 연결을 어느 쪽에서 보느냐의 차이. "글 → 태그된 제품"(정참조)과 "제품 → 그 제품이 태그된 글"(역참조).
- **좋아요 토글** = 같은 버튼을 누르면 켜고, 다시 누르면 끄는 방식.
- **멱등(idempotent)** = 같은 동작을 여러 번 해도 결과가 한 번 한 것과 같음. (좋아요를 두 번 눌러도 좋아요는 1개)
- **IDOR** = 남의 글·댓글을 주소만 바꿔 몰래 수정·삭제하려는 공격.

이 단계에서 만든 기능을 늘어놓으면 이렇습니다.

> 용도별 게시판 → 글 쓰기·읽기·수정·삭제(작성자만) → 댓글 → 좋아요(토글) → **글에 제품 태그** → 제품 화면에서 "이 제품 관련 글" 역으로 보기

### 게시판은 3칸으로 나눴습니다

| 카테고리 | 코드값 | 쓰임새 |
|---|---|---|
| 자유 | `free` | 가벼운 잡담·일상 |
| Q&A·팁 | `qna` | 질문과 노하우 공유 |
| 세일 정보 | `sale` | 할인·이벤트 정보 |

목록 화면에서 카테고리를 고르면(`?category=qna`처럼) 그 칸의 글만 추려서 보여 줍니다.

### 글에 제품을 붙인다 (이게 핵심)

beautalk은 원래 "피부에 맞는 제품을 추천해 주는" 서비스입니다. 그래서 커뮤니티 글에 **제품 태그**를 붙일 수 있게 했습니다.

- "추천받은 이 제품, 한 달 써 봤더니…" 같은 후기 글에 그 제품을 태그하면,
- 다른 사용자가 **제품 상세 화면**에서 "이 제품 관련 글 N개"를 바로 볼 수 있습니다.

즉, **추천 → 구매 고민 → 실제 후기**가 하나로 이어집니다. 광고 문구가 아니라 같은 사용자의 진짜 글이 제품 옆에 붙는 것이 장점입니다.

---

## ③ 왜 이렇게 했나 (선택지 비교)

### 비교 1 — 게시판을 하나로 둘까, 용도별로 나눌까

| 방식 | 장점 | 단점 |
|---|---|---|
| 단일 게시판 (한 칸) | 만들기 간단, 글이 한곳에 모임 | 잡담·질문·세일 정보가 뒤섞여 원하는 글을 찾기 어려움 |
| **용도별 분리 (우리 선택)** | 목적에 맞는 칸에서 보고 씀, 필터로 빠르게 탐색 | 카테고리 칸을 미리 정해 둬야 함 |

→ **용도별 분리**를 택했습니다. "질문하러 왔는데 세일 글만 잔뜩" 같은 불편을 막고, 글을 쓰는 사람도 어디에 쓸지 자연스럽게 정할 수 있기 때문입니다.

### 비교 2 — 글과 제품을 어떻게 연결할까

| 방식 | 설명 | 한계 |
|---|---|---|
| 글에 제품을 1개만 | 글 하나당 제품 하나 | "이 두 제품 같이 써 봤어요" 같은 글을 못 담음 |
| 본문에 제품 이름만 적기 | 그냥 텍스트로 언급 | 제품 화면에서 역으로 글을 찾을 수 없음 |
| **M2M 태그 (우리 선택)** | 글 ↔ 제품을 다대다로 진짜 연결 | 연결 테이블이 하나 더 필요(자동 처리됨) |

→ **M2M 태그**를 택했습니다. 글 하나에 제품 여러 개를 붙일 수 있고, 무엇보다 **제품 쪽에서 글을 거꾸로 찾는 기능**이 가능해지기 때문입니다.

---

## ④ 어떻게 만들었나

### 데이터 구조 (board 앱)

> 참고: 앱 이름을 흔한 `community`가 아니라 **`board`**로 둔 이유는, 파이썬 자체의 모듈명과 겹쳐 충돌이 날 수 있어서입니다.

- **Post(글)** — 글 1건. 카테고리·제목·본문을 담고, 주소(ID)를 **UUID**(추측 불가능한 임의의 긴 식별자)로 둬서 "1번, 2번…" 식으로 남의 글을 훑어보는 걸 막습니다.
- **Comment(댓글)** — 어느 글에 달린 댓글인지 연결됩니다.
- **PostLike(좋아요)** — "이 사용자가 이 글을 좋아요" 기록. 한 사람이 같은 글을 두 번 좋아요 못 하도록 **중복 금지 규칙**을 걸어 뒀습니다.
- **Post ↔ Product (M2M)** — 글과 제품의 다대다 연결. 제품 쪽에 `tagged_posts`라는 이름을 붙여, 제품에서 글을 거꾸로 꺼낼 수 있게 했습니다.

### 정참조와 역참조, 한 그림으로

```
   글(Post)  ────── 태그 ──────  제품(Product)
      │                              │
   정참조: 글 → 태그된 제품      역참조: 제품 → 태그된 글들
   "이 글에 어떤 제품?"          "이 제품 얘기한 글 어디?"
```

같은 연결선 하나를 **양쪽 끝에서** 보는 것뿐입니다. 그래서 화면도 양쪽에서 만들 수 있습니다.

- 글 상세에서 → 이 글이 태그한 제품 보기 (정참조)
- 제품 상세에서 → 이 제품을 태그한 글 목록 보기 (역참조)
  `GET /products/{제품ID}/posts/`

### 주소(API)를 관계로 읽히게 (RESTful)

주소만 봐도 "무엇의 무엇"인지 읽히도록 정리했습니다.

| 하는 일 | 주소(메서드) |
|---|---|
| 글 목록 / 작성 | `GET·POST /posts/` (목록은 `?category=`로 거름) |
| 글 상세 / 수정 / 삭제 | `GET·PATCH·DELETE /posts/{글ID}/` |
| 댓글 작성 | `POST /posts/{글ID}/comments/` |
| 댓글 삭제 | `DELETE /comments/{댓글ID}/` |
| 좋아요 켜기·끄기 | `POST·DELETE /posts/{글ID}/like/` |
| **이 제품 관련 글 (역참조)** | `GET /products/{제품ID}/posts/` |

`/products/{제품ID}/posts/`처럼 주소가 **"제품 안의 글들"**이라는 관계를 그대로 보여 주는 것이 핵심입니다.

### 안전장치

- **수정·삭제는 작성자만** — 글·댓글은 본인 것만 손댈 수 있게 매번 소유권을 확인합니다. 주소를 바꿔 남의 글을 건드리려는 시도(IDOR)는 막힙니다.
- **좋아요는 멱등** — 두 번 눌러도 좋아요는 1개로 유지됩니다.

### 프론트 화면 4종

| 화면 | 주소 |
|---|---|
| 목록 | `/community` |
| 작성 | `/community/new` |
| 상세 | `/community/:id` |
| 수정 | `/community/:id/edit` |

좋아요를 누른 상태는 화면을 새로 고쳐도 유지되도록 브라우저 저장소(localStorage)로도 한 번 더 보강했습니다.

---

## ⑤ 결과

- 용도별 게시판 3칸 + 글 CRUD + 댓글 + 좋아요까지 갖춘 커뮤니티가 완성됐습니다.
- **글과 제품이 양방향으로 연결**되어, 추천받은 제품 옆에 실제 사용자 후기 글이 붙는 구조가 됐습니다.
- 시드 데이터(글 7·댓글 5·좋아요 3)와 테스트 22개(CRUD·댓글·좋아요·IDOR 차단·역참조)로 동작을 검증했습니다.
- 명세서 **F1303(커뮤니티)**, **NF1304(페이지 5개 이상)** 요구사항을 충족했습니다.
