# 03. 협업 환경 — Git 전략

## ① 한 줄 요약

여러 명이 같은 코드를 동시에 고쳐도 충돌 없이 안전하게 합치기 위해, **`develop` 기본 브랜치 + 기능별 `feature` 브랜치 + Pull Request(코드 리뷰) 후 머지** 전략을 택했고, 그 결과 충돌을 최소화하며 백엔드·프론트가 병렬로 개발했다.

> **Git = 코드의 "변경 이력 기록 장치"이자 "되돌리기·합치기" 도구.** 누가 언제 무엇을 왜 바꿨는지 모두 남기고, 여러 명의 작업을 한 곳으로 안전하게 합쳐 준다. **GitHub = 그 기록을 인터넷에 올려 함께 보는 공간(클라우드 저장소).**

---

## ② 무엇을 했나

### 왜 브랜치 전략이 필요한가

여러 명이 **하나의 코드 더미를 동시에 고치면** 서로의 수정이 부딪힌다. A가 고친 줄을 B도 같은 시간에 고치면, 합칠 때 "둘 중 누구 걸 쓰지?" 하는 **충돌(conflict)** 이 난다. 정리되지 않으면 누군가의 작업이 통째로 사라지기도 한다.

그래서 **브랜치(branch)** 를 쓴다.

> **브랜치 = 원본 코드를 복사한 "나만의 작업 사본".** 내 작업이 끝날 때까지 남의 코드와 섞이지 않고, 다 되면 원본으로 합친다. 나무의 가지(branch)처럼 갈라졌다가 다시 줄기로 모인다.

### 우리가 택한 전략

| 구성 요소 | 역할 | 비유 |
|---|---|---|
| `develop` (기본 브랜치) | 항상 동작하는 "통합 줄기". 모든 기능이 여기로 모인다 | 본관 건물 |
| `feature/번호-이름` 브랜치 | 기능 하나당 가지 하나. 예: `feature/46-deploy-aws` | 공사 중인 별관 |
| Pull Request(PR) | "내 가지를 줄기에 합쳐 주세요" 요청 + **동료 리뷰** | 합치기 전 검수 신청서 |

작업 흐름: **`develop`에서 가지 치기 → 가지에서 기능 개발 → PR 올리기 → 동료가 리뷰 → 통과하면 `develop`에 머지.**

여기에 안전장치를 더했다.

- **브랜치 보호 룰셋**: `develop`에 직접 밀어 넣지 못하게 잠가, 반드시 PR을 거치게 강제.
- **PR 템플릿**(`.github/PULL_REQUEST_TEMPLATE.md`): 개요·작업 내용·테스트 방법·체크리스트를 빈칸으로 미리 제공해, 리뷰어가 항상 같은 형식으로 검토.
- **`.gitignore`**: 비밀번호·API 키(`.env`)와 빌드 산출물을 추적 대상에서 제외 → **실수로 비밀이 GitHub에 올라가는 것을 원천 차단**(시크릿 커밋 0건).
- **API 계약서 먼저 합의**: 백엔드·프론트가 "어떤 주소로 무엇을 주고받을지"를 문서로 먼저 못 박은 뒤 **병렬 개발** → 서로 기다리지 않고 동시에 진행.

## ③ 왜 이렇게 — 선택지 비교

브랜치 전략에는 대표적으로 세 갈래가 있다. 우리 규모(소수 인원, 빠른 반복)에 맞는 것을 골랐다.

| 선택지 | 어떤 방식인가 | 장점 | 단점 | 우리에게는 |
|---|---|---|---|---|
| **main에 직접 푸시** | 가지 없이 모두가 한 줄기에 바로 밀어 넣음 | 가장 단순 | 충돌·사고 빈발, 리뷰 없음, 망가지면 모두 멈춤 | ❌ 너무 위험 |
| **GitFlow** | main·develop·feature·release·hotfix 등 **가지 종류가 많음** | 대규모·정식 릴리스 관리에 강함 | 규칙이 복잡, 소규모엔 과함(오버엔지니어링) | ❌ 우리 규모엔 과중 |
| **GitHub Flow (우리 채택)** | `develop` 한 줄기 + 기능 가지 + PR 리뷰 | 단순하면서도 리뷰·보호 가능, 배우기 쉬움 | 정교한 릴리스 단계 구분은 약함 | ✅ **딱 맞음** |

**선택 이유**: 우리는 인원이 적고 기능을 빠르게 붙여 나가는 프로젝트다. GitFlow의 복잡한 단계는 필요 없고, 그렇다고 main 직접 푸시처럼 위험을 감수할 수도 없다. **"가볍지만 리뷰와 보호는 확실히"** 라는 GitHub Flow가 우리 규모에 가장 합리적이었다.

## ④ 어떻게 작동하나

### 커밋·PR 규칙

**커밋 메시지는 한글로, "무엇을 왜 했는지"가 드러나게** 적었고, 머리에 **종류 태그**를 붙여 한눈에 분류되게 했다.

| 태그 | 의미 | 실제 예시 |
|---|---|---|
| `feat` | 새 기능 | `feat: 글 다중 제품 태그 + 닉네임 연동` |
| `fix` | 버그 수정 | `fix: 게시글 좋아요 상태가 재진입 시 풀리는 문제` |
| `chore` | 잡일·정리 | `chore: 프론트 미사용 파일·코드 정리` |
| `docs` | 문서 | `docs: 배포 단계 반영 (HTTPS, OAuth, 트러블슈팅 상세)` |
| `refactor` | 동작은 그대로, 구조 개선 | `refactor(ui): 타이포 시스템 정리` |

PR은 **반드시 동료가 리뷰**한 뒤 머지했다. 실제 이력에도 `Merge pull request #52`, `#51`, `#50` … 처럼 PR을 거친 흔적이 줄줄이 남아 있다.

### 충돌이 났을 때 — 실제 사례

장기 작업 브랜치(배포 준비 `46-deploy-aws-ec2…`)는 본 줄기 `develop`과 오래 떨어져 있었다. 그 사이 `develop`에는 프론트 UI·API 관련 수정이 계속 머지됐다.

- **원인**: 배포 브랜치와 `develop`이 **같은 프론트 설정 파일(API 주소 설정 등)을 각자 다르게 수정** → 두 줄기의 같은 줄이 달라져 충돌.
- **푼 방법**: 배포 브랜치에서 `develop`을 다시 **머지(merge)** 해 최신 변경을 끌어와, 충돌 난 부분을 **"어느 쪽이 옳은 최신값인지" 직접 판단해 한 줄로 정리**했다. 실제로 이력에 `Merge remote-tracking branch 'origin/develop' into 46-deploy-…` 커밋이 남아 있다.
- **교훈**: 오래 떨어진 브랜치일수록 **자주 `develop`을 끌어와 동기화**해야 충돌이 작게 끝난다. 한 번에 몰아서 합치면 충돌 덩어리가 커진다.

---

## ⑤ 결과·배운 점

- **충돌 최소화**: 기능별로 가지를 나눠 작업해 서로의 코드를 거의 건드리지 않았고, 충돌이 나도 작은 단위라 금방 풀렸다.
- **품질 향상**: 모든 변경이 PR 리뷰를 통과 → 실수·버그를 머지 전에 걸러냈다.
- **병렬 개발**: API 계약서를 먼저 합의해 백엔드·프론트가 서로 기다리지 않고 동시에 진행했다.
- **보안 사고 0건**: `.gitignore`로 `.env`·키를 제외해 비밀이 한 번도 GitHub에 올라가지 않았다.

### 명세서 NF1301(Git 활용) 충족 포인트

| 요구 | 우리가 충족한 방식 |
|---|---|
| 버전 관리 도구 활용 | GitHub 기반 형상 관리, 모든 변경 이력 추적 |
| 브랜치 전략 | `develop` + `feature/번호-이름` + PR 리뷰 후 머지 |
| 협업 규칙 | 한글 커밋 규칙(feat/fix/chore/docs), PR 템플릿, 브랜치 보호 룰셋 |
| 안전한 협업 | `.gitignore`로 비밀·빌드산출물 제외, 리뷰 강제 |
