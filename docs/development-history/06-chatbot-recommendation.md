# 06. 챗봇 — 대화와 추천 분리

## ① 한 줄 요약

챗봇이 한 화면에서 "수다도 떨고 추천도 하는" 만능 일꾼이 되려다 헷갈리던 것을, **대화만 하는 단계**와 **추천만 하는 단계** 둘로 쪼개고, 서버는 대화를 기억하지 않는 가벼운 구조(Stateless)로 두며, AI 응답을 정해진 형식(JSON)으로 강제하고, 빙빙 돌던 대화를 "쓸 수 있는 정보만 묻는" 직행 대화로 끌어올린 단계입니다.

---

## ② 무엇을 했나 (쉽게)

이 단계의 핵심은 **"하나의 AI에게 두 가지 일을 동시에 시키지 않는다"** 입니다.

용어부터 쉽게 풀어 두겠습니다.

- **LLM** = 사람 말로 묻고 답하는 AI(대화형 인공지능). 우리는 GMS라는 외부 AI 서버를 호출해 씁니다.
- **JSON** = 컴퓨터가 정확히 읽을 수 있도록 `{ "키": "값" }` 형태로 정리한 데이터 표기법입니다.
- **Stateless(무상태)** = 서버가 지난 대화를 **기억하지 않고**, 매번 필요한 내용을 통째로 받아 처리하는 방식입니다.

### 왜 단계를 나눴나 — 만능 일꾼의 혼란

처음 챗봇은 `POST /api/v1/chat/` 하나가 **대화 응답과 제품 추천을 한꺼번에** 처리하려 했습니다. 문제는 AI가 추천을 위해 JSON으로 답해 버리면, **그 JSON 덩어리가 채팅 말풍선에 그대로 노출**되는 일이 벌어졌다는 점입니다. 사람에게 건넬 말과 컴퓨터가 읽을 데이터가 한 출구로 뒤섞여 나온 것입니다.

한 사람에게 "손님과 자연스럽게 대화도 하고, 동시에 정확한 주문서도 작성하라"고 시키면 둘 다 어설퍼지듯, AI도 마찬가지였습니다. 그래서 **역할을 둘로 갈랐습니다.**

```
[① 대화 단계]  POST /api/v1/chat/
   자연어 텍스트만 주고받는다 (채팅 경험)
   "향에 민감한 편이신가요?"  ← 사람에게 건네는 말만
        │
        │  사용자가 [✨ 추천받기] 클릭
        ▼
[② 추천 단계]  POST /api/v1/recommend/
   그동안의 대화 전체를 근거로 제품 3개를 구조화해 반환
   { content: "...", products: [...] }  ← 컴퓨터가 읽는 데이터
```

- **대화 단계**는 오직 **자연어**만 다룹니다. 채팅창에는 깔끔한 말풍선만 보입니다.
- **추천 단계**는 사용자가 버튼을 누른 순간에만 작동해, 제품 카드에 쓸 **정돈된 데이터**를 만들어 냅니다.

이렇게 하니 채팅창에는 말만, 추천 카드는 추천 단계에서만 나옵니다. 각 단계가 한 가지 일만 하므로 AI도 헷갈리지 않습니다.

### 추천은 언제 시작되나 — `ready` 신호 하나

대화 단계에서 AI는 매번 답과 함께 `ready`(true/false)라는 신호를 같이 보냅니다. "이제 추천할 만큼 정보가 모였나?"에 대한 솔직한 판단입니다.

- `ready=true`가 되면 프론트가 **[추천받기] 버튼을 반짝이게** 강조합니다.
- 단, 사용자는 `ready`와 무관하게 **언제든** 추천을 누를 수 있습니다(중간 추천 허용).
- 한 번 true가 된 강조는 유지(sticky)하고, 새 대화를 시작하면 다시 꺼집니다.

처음에는 "준비도 0~100점" 같은 숫자 게이지를 쓰려 했지만, AI가 매기는 점수가 들쭉날쭉 요동쳐 UI도 디버깅도 손해라, **`ready` 불리언(켜짐/꺼짐) 하나로** 단순화했습니다.

---

## ③ 왜 이렇게 했나 — 선택지 비교

### (a) 한 단계로 다 처리 vs 두 단계로 분리

| 방식 | 채팅창에 보이는 것 | AI의 부담 |
|------|---------------------|-----------|
| 한 단계(기존) | 자연어 + JSON 덩어리가 **뒤섞임** | 대화·추천을 동시에 → **혼란** |
| **두 단계(선택)** | 대화엔 말만, 추천 카드는 따로 | 각 단계가 **한 가지 일만** |

> 핵심: **"역할을 나누면 각자가 자기 일만 잘하면 된다."** 대화는 대화답게, 추천은 추천답게.

### (b) 서버가 대화를 저장할까 — 상태 보관 vs Stateless

| 방식 | 대화 내역(history)을 | 장단점 |
|------|----------------------|--------|
| 서버 저장 | 서버 DB에 보관 | 서버가 무거워지고, 대화 경계 관리가 복잡 |
| **Stateless(선택)** | **프론트가 들고** 매 요청에 전송 | 서버는 가볍고, "새 대화" 경계를 프론트가 명확히 관리 |

우리는 **Stateless**를 택했습니다. 서버는 대화를 기억하지 않고, 프론트가 `history[]`(지금까지 주고받은 말 목록)를 매 요청마다 통째로 보냅니다. 서버는 "지금 받은 것"만 보고 답하면 되니 단순하고, 어디까지가 한 대화인지(새 대화로 리셋할 시점)는 history를 들고 있는 프론트가 가장 잘 알기에 그 책임도 프론트에 둡니다.

---

## ④ 어떻게 작동하나

### AI 응답을 정해진 형식으로 강제 — JSON 모드 없이

대화 단계의 AI는 `{ "content": "...", "ready": false }` 형태로 답해야 합니다. `content`는 채팅 말풍선에 그릴 자연어, `ready`는 버튼 강조용 신호입니다.

문제는 우리가 쓰는 **GMS가 "JSON으로만 답해" 기능(json_mode)을 지원하지 않는다**는 점입니다. 그래서 **프롬프트(AI에게 주는 지시문)로 형식을 강제**했습니다 — "반드시 아래 JSON 형식으로만 답하라"고 못 박고, 받은 답을 파싱해 `content`와 `ready`로 갈라 냅니다.

추천 단계도 같은 원리입니다. AI에게 후보 제품 목록을 보여 주고 **"이 목록에 있는 정확한 id 3개만 골라라"**고 시킨 뒤, 백엔드가 그 id로 DB를 다시 조회해 **실제 존재하는 제품만** 반환합니다. AI가 없는 제품을 지어내도(환각) DB 조회에서 걸러집니다.

### AI 서버 장애를 사용자 말로 번역 — 에러 처리

외부 AI 서버는 가끔 느리거나 끊깁니다. 우리는 그 기술적 실패를 **명확한 상태코드로 번역**해 프론트가 일관되게 안내하도록 했습니다.

| 상황 | 변환 | 사용자에게 |
|------|------|------------|
| AI 응답이 너무 느림(Timeout) | **504** | "잠시 후 다시 시도해주세요" |
| AI 서버 연결 실패(ConnectionError) | **502** | "AI 서버 연결에 실패했습니다" |
| 필수 입력 누락(content 없음) | **400** | 입력 안내 |

에러는 전부 `{ "error": "..." }` 공통 포맷으로 돌려, 프론트는 어떤 실패든 같은 방식으로 처리할 수 있습니다.

### 추천 결과를 배치로 기록 — 부모·자식 구조

추천을 한 번 받을 때마다 그 묶음을 통째로 기록합니다.

```
Recommendation (추천 1회 = 배치, 부모)
   ├─ 배치 요약("여드름 자국 + 민감성을 고려해 3가지를 골랐어요")
   └─ RecommendedProduct (자식) × 최대 3
        ├─ 제품 A + 이 제품을 고른 이유(reason)
        ├─ 제품 B + 이유
        └─ 제품 C + 이유
```

이렇게 부모·자식으로 묶으면 ① 추천 한 묶음을 식별하고 ② 같은 제품이 다른 날 또 추천돼도 각각 별도 기록으로 남으며(이벤트 로그) ③ 배치 요약까지 보존됩니다. 히스토리 화면은 이 배치를 최신순 타임라인으로 보여 줍니다.

## ⑤ 결과 · 배운 점

### 명세서 F1301(사용자 추천)·F1302(API 활용) 충족

- **F1301(사용자 추천)** — 대화로 모은 정보와 피부 프로필을 근거로 실제 DB의 제품 3개를 골라, 제품별 이유와 함께 추천합니다.
- **F1302(API 활용 = LLM)** — 외부 AI(GMS LLM)를 호출해 대화·추천을 수행하고, AI가 지어낸 제품은 DB 검증으로 걸러 내 신뢰를 지킵니다.

### 빙빙 돌던 대화를 직행으로 — 대화 품질 개선

분리만으로 끝이 아니었습니다. 실사용에서 대화가 **자꾸 헛도는** 문제가 드러났습니다.

| 상황 | Before (헛도는 대화) | After (직행) |
|------|----------------------|--------------|
| "성능 적당히 좋으면 됨" | SPF 수치를 **표현만 바꿔 4번** 반복 질문 | **"선크림·예산 2만원 이하 확인. 추천으로 넘어갑니다."** `ready=true` |
| 새 대화 "뭘 골라야 할지 모르겠어" | 젤·향료처럼 **데이터에 없는 축**을 질문 | **"가격대부터 알려주실 수 있을까요? '2만원 이하'처럼요."** |
| "5천원 이하 선크림"(0건) | (재고를 몰라 헛약속) | **"5천원 이하 선크림은 확인되지 않습니다. 1만원대까지 늘려도 될까요?"** |

뿌리 원인은 하나였습니다 — **챗봇이 "추천 단계가 실제로 쓸 수 있는 정보가 무엇인지"를 모른 채 대화했다**는 것입니다. 그래서 데이터에 없는 향료·성분·SPF 세부 수치를 멋대로 캐묻고, 사용자가 답해도 추천에 못 써 대화가 헛돌았습니다.

처방은 챗봇을 **"실제로 거를 수 있는 축"에만 묶는 것**이었습니다.

- **쓰는 정보만 질문** — 제품군·제형(정해진 10종)·가격대·피부 고민. 이 안에서만 묻습니다.
- **못 쓰는 축 차단** — 향료·성분·세부 텍스처·정확한 SPF는 묻지 않고, **사용자에게 성분표를 확인하라고 일을 떠넘기지 않습니다.**
- **루프 차단** — "모름/적당히"도 유효한 답으로 받아 슬롯을 넘기고, 같은 질문을 다시 묻지 않으며, 어려운 용어를 먼저 던지지 않습니다.
- **근거 있는 대화** — 대화 중 **실제 재고를 SQL로 읽어** 프롬프트에 주입합니다. 봇이 "지금 조건에 맞는 제품 약 N개(가격 X~Y원)"를 알고 대화하니, 0개면 조건을 넓히도록 유도할 수 있습니다.

### 배운 점

가장 크게 배운 것은 **"AI에게 한 번에 한 가지 일만, 그것도 실제로 가능한 범위 안에서 시켜야 한다"**는 점입니다. 대화와 추천을 한 일꾼에게 동시에 맡기면 둘 다 어설퍼지고, AI가 데이터에 없는 것까지 물으면 대화는 끝없이 헛돕니다. 역할을 나누고(분리), 쓸 수 있는 정보에 묶어 두자(그라운딩) 대화가 비로소 목적지로 직행했습니다.
