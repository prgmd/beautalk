## 2. 지금 어디까지 왔나 (쉬운 말)

한 문단으로: **로그인·온보딩·찜·제품·챗봇·추천·커뮤니티(백엔드)·RAG 검색·PostgreSQL 전환·보안까지 거의 다 됐다.**
지난주에 **데이터 정제**(중복 제품 53건 제거, 요약 누락 채움)도 끝냈다.

지금 막힌 단 하나의 큰 구멍은 **추천의 정확도**다.

> **쉽게 말하면:** "로션 추천해줘"라고 했는데 AI가 비슷해 보이는 **크림**을 추천한다.
> AI가 의미(느낌)로만 비슷한 걸 찾다 보니, "이건 로션이 아니다"라고 **거절을 못 한다.**
> 이걸 고치는 게 지금 작업(**하이브리드 추천**)이다.

### A. 하이브리드 추천 〔지금 핵심〕

> **쉽게 말하면:** 추천을 2단계로 나눈다.
> ① 먼저 **SQL로 "조건 안 맞는 제품을 아예 빼버린다"** (로션 아니면 후보에서 제외, 예산 밖이면 제외).
> ② 그다음 남은 것 중에서 AI가 고른다.
> → AI는 **조건 맞는 것만** 보게 되니, 틀린 추천이 **구조적으로 불가능**해진다.
> 세부 취향(끈적임·진정감 등)은 리뷰 요약 기반 의미 검색(RAG)이 맡는다 — **하드 조건은 SQL, 부드러운 취향은 AI.**

| # | 작업 | 파일 | 비고 |
|---|------|------|------|
| A1 | `Product.form`(제형) 필드 + 마이그레이션 | `products/models.py` | **선행 1번.** 제형 칸이 없으면 거를 수가 없음 |
| A2 | 제품명 규칙 파싱으로 `form` 백필 | `management/commands/backfill_form.py` (신규) | "로션/스킨/크림…" 키워드 매칭 (계약 §4) |
| A3 | 대화에서 제약 추출 (`_extract_constraints`) | `chat/views.py` | 규칙(정규식+enum) 우선 → 부족 시 LLM. **빈손이면 기존대로 폴백** |
| A4 | `_recommend_candidates`에 SQL 필터 | `chat/views.py` | price/form/category로 후보 선거름 |
| A5 | 완화(graceful degradation) + `constraints` 응답 | `chat/views.py`, `serializers.py` | 조건 부족하면 단계적으로 풀고 **무엇을 풀었는지 표기** |
| A6 | 응답에 `form`·`meets` 직렬화 | `serializers.py` | 프론트 배지용 |
| A7 | 프롬프트에 `{price}원`·`{form}` 추가 | `chat/views.py` | LLM 이유 작성·동률 선택용 (보조) |
| A8 | 계약서 보완 (추출 단계 1급 승격 등) | `recommend-hybrid-contract.md` | 아래 "계약 보완" 참고 |

**진행 순서:** `A1·A2(데이터)` → `A3·A4(필터)` → `A5·A6(응답)` → `A7(프롬프트)`.
`form` 데이터가 있어야 필터가 의미 있으니 **A1부터** 시작.

**결정한 기본값 (프론트 합의 없이 단독 진행 가능):**
- 완화 순서: 가격 ±10,000 → 제형 해제 → 카테고리 해제 (예산 최대한 존중)
- `MIN_POOL`(완화 트리거 최소 후보 수): **3** — 추천은 3개라 후보 ≥3이면 답을 만들 수 있음. 3개 미만일 때만 완화(조건 위반을 최소화). 정확히 3개면 LLM 선택 여지는 없지만 모두 조건을 지킨 유효 제품이라 OK.
- form enum: 계약 §4의 10종 그대로 (toner/lotion/essence/serum/cream/mist/suncream/cleanser/pad/mask)

**계약서 보완(A8) 핵심 3가지** — 논의로 합의했으나 아직 문서에 약하게 반영됨:
1. **제약 추출을 1급 단계로** — 지금 계약 §3엔 "(선택)"으로 묻혀 있음. 이게 **백엔드 자급자족**(프론트 칩 없어도 동작)의 핵심.
2. **FE 칩 vs 대화 추출 우선순위** — 명시 칩 > 추출(빈 축만 보강).
3. **하드(SQL)/소프트(임베딩) 분리 원칙**을 §0에 명문화.

**확장 아이디어 (후속):**
- **추천 교체(삭제 → 다음 순위 채움)** — 결과 3종 중 하나를 삭제하면 풀의 다음 순위가 올라와 채운다. 파이프라인이 이미 15개 후보(`RECOMMEND_POOL_SIZE`)를 뽑아 3개만 쓰므로 "다음 순위"가 공짜로 존재.
  - 구현(추천): stateless `POST /recommend/replace` — `{history, filters, exclude_ids}` → `_recommend_candidates` 재실행 → 이미 보여준 거 제외 → 다음 1개 + reason 1콜(gpt-4o). 풀(상태) DB 저장 불필요.
  - 결정할 것: 교체품 reason 생성(추천)·풀 고갈 처리("더 없음")·히스토리는 뷰 한정(원본 로그 보존)·replace 전용 throttle.

### B. LLM 관측 〔개발 중 곁들임〕

> **쉽게 말하면:** AI가 "왜 그렇게 답했는지" 안 보이면 프롬프트 튜닝이 깜깜이다.
> 추천 프롬프트를 한창 만질 지금, **프롬프트·응답·추출결과를 들여다보는 창**을 켜 둔다.
> 운영 감시가 아니라 **개발 디버깅**이 진짜 목적 — 그래서 "마지막"이 아니라 "지금".

- **LangChain(프레임워크)은 도입하지 않는다.** 이미 `_call_gms`가 30줄로 깔끔하고, 하이브리드는 Django ORM+pgvector 도메인 로직이라 LangChain이 오히려 방해.
- **✅ 배선 완료** — `@traceable`를 `_call_gms`·`_resolve_constraints`·`_recommend_candidates`에 부착. [chat/observability.py](../backend/chat/observability.py)가 langsmith 미설치/미설정 시 **no-op**라 안전.
- **활성화(키 필요):** `pip install langsmith` + `.env`에 `LANGSMITH_TRACING=true`·`LANGSMITH_API_KEY=...`(·`LANGSMITH_PROJECT=beautalk`). 그러면 입력·출력·지연이 LangSmith 대시보드로.
  - 활용: 규칙 추출이 얼마나 놓치는지 관찰 → LLM 폴백 도입 시점 판단 근거.

### C. 데이터 품질 후속 〔A의 선행 일부〕

> **쉽게 말하면:** 필터가 정확하려면 **데이터가 깨끗**해야 한다. 가격이 틀리거나 카테고리가 거칠면 SQL 필터도 헛돈다.
> 중복 제품(53건)은 이미 제거했고, 남은 둘:

- **가격 불일치 정정** — 일부 제품 가격이 현재 올리브영과 다름.
- **카테고리 대분류 정규화** — 지금 `category`가 거친 대분류라, 하이브리드의 `category` 필터를 켜려면 **정규 목록 고정**이 선행.
- 상세: 메모리 `data-quality-backlog`.

### F. 챗봇 대화 품질 〔✅ Phase 1~3 구현됨〕

> **해결 요약 (2026-06-24):** ① 프롬프트를 추천 필터 축(제품군·제형 enum·가격·고민)에 묶고
> 못 쓰는 축(향료·성분·세부 텍스처·SPF)을 차단 + "모름/적당히" 수용·재질문 금지 규칙
> ([_build_chat_prompt](../backend/chat/views.py)). ② LangSmith 관측 배선([observability.py](../backend/chat/observability.py)).
> ③ 대화 중 실제 재고를 SQL로 읽어 주입(_availability_hint) — 봇이 데이터에 근거해 대화.
> 라이브 검증: 빙빙 돌던 대화 → `ready=true` 직행, "5천원 선크림 없음 → 1만원대로?" 유도.
> 아래는 원래 문제 분석(기록 보존).

> **쉽게 말하면:** 대화 챗봇이 사용자 말귀를 못 알아듣고 같은 걸 빙빙 돌려 묻는다.
> (2026-06-24 관찰) ① "선크림 성능 적당히 좋으면 됨"이라 해도 SPF 수치를 4번 반복 질문,
> "매트한 마감" 같은 전문어를 먼저 던짐. ② 데이터에 없는 축("젤" 제형·"향료/성분")을
> 캐묻고, 사용자가 모른다니까 "성분표 확인해 주세요"라고 **봇 할 일을 사용자에게 떠넘김.**

- **원인 추정:** `_build_chat_prompt`의 "정보를 하나씩 물어봐라" 규칙이, 사용자가 "모름/상관없음/적당히"로 답해도 그걸 유효한 답으로 수용 못 하고 같은 슬롯을 재질문하게 만듦.
- **개선 방향:**
  - 사용자가 "모름/상관없음/적당히"로 답하면 → **그 슬롯은 건너뛰고 추천으로 진행**(무한 캐묻기 금지).
  - **이미 물은 항목 재질문 금지**(같은 질문 표현만 바꿔 반복 방지).
  - 전문 용어는 쉬운 말로 풀고, **용어를 먼저 묻지 말 것**.
  - **시스템이 못 거르는 속성은 묻지 말 것** — "젤"(form enum에 없음)·"향료/성분"(데이터 없음, 기피성분 필터는 범위 밖)을 물어봐야 답에 못 씀. 질문은 **실제 필터 축(form enum·가격·피부타입/고민)으로 한정**.
  - **사용자에게 일 떠넘기기 금지** — "성분표 확인해 주세요"처럼 봇이 할 일을 사용자에게 미루지 말 것.
  - **챗봇을 데이터 어휘로 그라운딩** — 챗봇 프롬프트에 "실제 존재하는 제형(form enum)·필터 축"을 주입해, 데이터에 없는 하위 구분을 **질문으로 만들지 않게 차단**한다. (예: 선크림은 우리 데이터상 단일 `suncream`이라 젤/스틱/로션/크림 구분이 없음 → 그 질문 자체가 헛돔.) 지금 챗봇은 RAG로 데이터를 안 읽고 freestyle이라 "자기 맘대로" 감.
  - 텍스처(젤 등)는 하드 필터 불가 → **임베딩 소프트 신호로만** 반영(현재 약함). 구조화하려면 form 하위에 texture 필드를 두는 별도 데이터 작업 필요(범위 밖, 후속).
  - 2~3턴 내 추천 가능하면 `ready=true`로 빨리 전환.
- 손볼 곳: [_build_chat_prompt](../backend/chat/views.py). **테마 B(LangSmith)로 이런 대화를 관찰**하면 튜닝 근거를 데이터로 확보 — F와 B는 짝.

## 4. 그래서 지금 뭐부터? (한 줄)

**A1(`form` 필드) → A2(백필) → A4(SQL 필터)** 순으로 가면, "로션 요청에 크림" 문제가 가장 빨리 사라진다.
관측(B)은 A3·A7 프롬프트를 만지기 시작할 때 가볍게 곁들인다.
