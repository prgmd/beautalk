# 챗봇 대화 품질 트러블슈팅

> 추천 대화 챗봇이 사용자 의도를 못 잡고 빙빙 돌던 문제의 진단·해결 기록.
> 작성: 2026-06-24 · 관련 코드: [chat/views.py](../backend/chat/views.py), [chat/observability.py](../backend/chat/observability.py)
> 백로그 항목: [README.md](README.md) §3-F

---

## 1. 증상 (실사용 관찰)

대화 챗봇(`POST /api/v1/chat/`)에서 세 가지 패턴이 반복됐다.

| # | 증상 | 실제 대화 |
|---|------|-----------|
| ① | **빙빙 돌려말함 / 의도 무시** | "성능 적당히 좋으면 됨"이라 해도 SPF 수치를 **표현만 바꿔 4번** 반복 질문 |
| ② | **어려운 용어** | 사용자가 묻기도 전에 "매트한 마감을 선호하나요?" 같은 전문어를 먼저 던짐 |
| ③ | **데이터에 없는 축을 캐물음** | "젤/로션/크림 중 골라주세요"(젤은 form enum에 없음), "향료 여부 알려주세요"(성분 데이터 자체가 없음) |
| ④ | **사용자에게 일 떠넘김** | "그걸 내가 어찌 아니"라니까 **"성분표에 향료 표기 있는지 확인해 주세요"** 라고 사용자에게 라벨 확인을 시킴 |

---

## 2. 원인 분석

증상 4개는 표면이고, **뿌리는 하나**다.

> **챗봇이 "추천 단계가 실제로 쓸 수 있는 정보가 뭔지"를 모른 채 대화했다.**

구버전 `_build_chat_prompt`는 카테고리 목록만 주고 *"필요한 정보를 하나씩 물어봐라"* 라고만 시켰다. 그 결과:

- **그라운딩 부재** → 데이터에 없는 축(젤·향료·성분·SPF 수치)을 멋대로 질문으로 만듦. 사용자가 답해도 추천 단계가 못 쓰니 대화가 헛돎.
- **"하나씩 물어봐라"의 부작용** → 사용자가 "모름/적당히"로 답해도 그걸 유효한 답으로 **수용하지 못하고** 같은 슬롯을 재질문하는 루프.
- **freestyle** → 챗봇이 실제 제품 데이터를 전혀 읽지 않아, 있지도 않은 조건을 약속하거나 사용자에게 떠넘김.

핵심 처방: **챗봇을 "추천 필터 축"에 묶고(grounding), 행동 규칙으로 루프를 차단한다.**

## 3. 해결 (Phase 1~3)

### Phase 1 — 프롬프트 그라운딩 + 행동 규칙
`_build_chat_prompt` 재설계. ([chat/views.py](../backend/chat/views.py))

- **쓰는 정보만 질문** — 제품군(카테고리) · 제형(`Product.FORM_CHOICES` 10종) · 가격대 · 피부 고민. 이 안에서만 묻게 함.
- **못 쓰는 축 차단** — "향료/성분·세부 텍스처(젤/스틱)·SPF 정확한 수치는 묻지 마라. 사용자에게 성분표를 확인하라고 시키지 마라."
- **행동 규칙** — ① "모름/상관없음/적당히"는 유효한 답 → 슬롯 스킵 ② 같은 질문 재질문 금지 ③ 쉬운 말, 용어 먼저 묻지 않기 ④ 제품군 특정되면 빠르게 `ready=true`.

### Phase 2 — LangSmith 관측 배선
[chat/observability.py](../backend/chat/observability.py) — `@traceable`를 `_call_gms`·`_resolve_constraints`·`_recommend_candidates`에 부착.

- **LangChain(프레임워크)은 미도입** — 직접 호출이 더 단순. 관측 도구 LangSmith만 얹음.
- **미설치/미설정 시 no-op** — `from langsmith import traceable` 실패하면 원함수 그대로 반환하는 더미 데코레이터라 운영·테스트에 영향 0.
- **활성화:** `pip install langsmith` + `.env`에 `LANGSMITH_TRACING=true`·`LANGSMITH_API_KEY=...`·`LANGSMITH_PROJECT=beautalk`. (langsmith==0.7.37은 requirements에 포함)

### Phase 3 — 라이브 데이터 그라운딩
`_availability_hint` — 대화 중 **실제 재고를 SQL로 읽어** 프롬프트에 주입. ([chat/views.py](../backend/chat/views.py))

- 하이브리드 추천의 제약 추출(`_resolve_constraints`) + 필터(`_filtered_qs`)를 **재활용** — 임베딩 호출 0, 가벼운 count + min/max 쿼리뿐.
- 봇이 "현재 조건에 맞는 제품 약 N개 (가격 X~Y원)"를 알고 대화 → 데이터에 근거해 판단(0개면 조건 넓히도록 유도).

### 보너스 — 가격 추출 보강
`_extract_price`가 만원만 읽던 것을 **천원·"N만M천원"** 까지 지원. ("5천원 이하" → `(None, 5000)`, "2만5천원 이하" → `(None, 25000)`)

## 4. 검증 (Before → After)

라이브 GMS 호출로 동일 상황 재현.

| 상황 | Before (관찰) | After (수정 후) |
|------|---------------|-----------------|
| "성능 적당히 좋으면 됨" | SPF 수치 4번 반복 질문 | **"선크림·예산 2만원 이하 확인. 추천 단계로 넘어가겠습니다."** `ready=true` |
| 새 대화 "뭘 골라야 할지 모르겠어" | 젤/향료 등 못 쓰는 축 질문 | **"가격대부터 알려주실 수 있을까요? '2만원 이하'나 '2~3만원대'처럼요."** (쓰는 축 + 쉬운 예시) |
| "5천원 이하 선크림" (0건) | — | **"5천원 이하 선크림은 확인되지 않습니다. 예산을 1만원대까지 늘려도 될까요?"** (재고 읽고 유도) |

- 전체 테스트 **58개 통과** (회귀 없음).

## 5. 한계·후속

- **텍스처(젤/스틱)는 여전히 하드 필터 불가** — `form`은 선크림을 단일 `suncream`으로만 분류. 젤/스틱 하위 구분은 데이터에 없어 임베딩 소프트 신호로만 약하게 반영. 구조화하려면 `form` 하위 `texture` 필드 + 데이터 작업 필요(범위 밖).
- **규칙 추출의 빈틈** — `_extract_price`·`_extract_forms`는 규칙 기반이라 돌려 말한 표현("가성비", "산뜻한 거")은 못 잡음. LangSmith로 놓치는 빈도를 관찰해 LLM 추출 폴백 도입 시점을 판단.
- **프롬프트 회귀 감시** — 프롬프트는 테스트로 강하게 고정하기 어렵다. LangSmith 트레이스를 주기적으로 보며 새 회귀(빙빙 돌기 재발 등)를 잡는다.

## 6. 응답 지연 (LLM 호출 시간) — gpt-5 추론 오버헤드

> **증상:** 추천 응답이 너무 느림(체감 ~25초).

**측정** (단계별 직접 계측, LangSmith로도 동일하게 보임):

| 단계 | 시간 | 비중 |
|------|------|------|
| 임베딩(embed) | ~1.0s | 4% |
| 후보선정 SQL·필터 | ~0.1s | — |
| **LLM 호출(`_call_gms`)** | **~24s** | **~96%** |

→ 병목은 **100% LLM 호출**. `gpt-5-nano`가 **추론(reasoning) 모델**이라 출력 전 숨은 추론에 시간을 쓴다.

**해결:** `reasoning_effort`를 낮춰 추론 깊이 축소. (실측)

| 설정 | LLM 시간 |
|------|----------|
| 기본(full) | ~20–24s |
| `low` | ~5–8s |
| `minimal` | ~2–3.5s |

- **대화(chat)** → `minimal` (인터랙티브·단순): ~2s
- **추천(recommend)** → `low` (3개 선택에 판단 여지): ~8s
- 환경변수 `GMS_REASONING_EFFORT`(기본 `low`)로 조절, `_call_gms`에서 payload에 주입.
- 출력 품질 유지 확인(추천 3개 정상 선택·이유 작성, 대화 정상).

> **교훈:** 추론 모델은 **작업에 맞게 추론 깊이를 조절**해야 한다. 단순 구조화 출력(JSON 선택)에 full 추론은 낭비. LangSmith의 `gms_call`·`embed` 노드 지연으로 병목을 한눈에 격리할 수 있다.

> **후속(2026-06-24):** 이 `reasoning_effort` 튜닝(24s→8s) 이후, 모델 5종을 실측 비교해
> **비추론형 `gpt-4o`로 교체**(추천 3.6s, 속도·품질 모두 1위)했다. 추론형은 깊이를 낮춰도
> 비추론형보다 느렸다는 게 결론. 상세: [model-selection-report.md](model-selection-report.md).
