# 제품 데이터 정제 (중복 제거 + 리뷰 기반 ai_summary 완비)

> 추천 결과가 이상하다는 제보에서 출발해, 제품 데이터의 **중복·결측·부정확**을
> 차례로 진단하고 고친 작업 정리. 핵심은 *"셀레니움 재크롤링"으로 가려던 길을
> 데이터를 보고 **"리뷰 API + LLM 요약"** 으로 틀어, 셀레니움 없이 끝낸 것.

---

## 1. 발단 — 추천이 이상하다

추천 카드에서 두 가지 증상이 보고됐다.

1. **쿼리와 안 맞는 제품**: "지성·2~3만원대 로션/스킨 세트"를 물었는데 크림·앰플·토너가 섞여 나옴.
2. **가격 불일치**: 추천 카드의 닥터지 수딩크림이 **27,600원**인데, 카드의 올리브영 링크를 열면 **38,000원**.

증상만 보면 "추천 로직(RAG) 문제" 같지만, 데이터를 열어보니 **근본 원인은 데이터 품질**이었다.

## 2. 진단 — 문제는 셋(사실은 넷)

DB(`Product` 103→실제 156건)를 뜯어보니:

| # | 문제 | 수치 | 원인 |
|---|------|------|------|
| A | **중복 적재** | 156건 중 53건이 중복 | 크롤링이 URL 비교로만 중복을 걸러, 같은 제품이 여러 카테고리에서 다른 URL 파라미터로 재저장 |
| B | **ai_summary 결측** | 103(고유) 중 40건이 빈 값 | 크롤링이 상세 단계에서 중간에 멈춤 |
| C | **가격 부정확** | 일부 제품 DB가격 ≠ 현재가 | 크롤링 시점·셀렉터 문제 |
| D | **리뷰 결측**(B 조사 중 발견) | 빈 40건이 **리뷰도 0개** | B와 같은 원인(상세 크롤링 중단) |

> **핵심 통찰:** A·B·D는 모두 *크롤링이 같은 제품을 중복으로 긁고, 상세는
> 덜 긁은* 한 뿌리에서 나왔다. 그래서 "추천 알고리즘"이 아니라 **데이터부터**
> 고쳐야 했다.

### goodsNo — 진짜 고유 식별자

올리브영 URL의 `goodsNo`(예: `A000000253384`)가 제품의 진짜 고유키다. URL 전체로
비교하면 파라미터(`&tab=`, `dispCatNo` 등) 차이로 같은 제품이 달라 보이지만,
`goodsNo`로 묶으면 정확히 갈린다. 실제로:

```
goodsNo 그룹 = 103  (= name 고유 103과 정확히 일치)
중복그룹 = 50,  제거 가능 = 53,  goodsNo 없는 URL = 0
```

## 3. 해결 ① — 중복 제거 (`dedupe_products`)

`goodsNo` 기준으로 묶어 그룹마다 **대표 1건만 남기고** 나머지를 지운다.

- **대표 선정 우선순위**: 임베딩 보유 > ai_summary 보유 > 리뷰수 — RAG 검색 자산을 잃지 않도록.
- **참조(FK) 재연결**: 삭제되는 제품을 가리키던 `Like`·`RecommendedProduct`를 대표로 옮긴다(데이터 손실 방지). `board.Post`는 `goodsNo` 미머지 상황을 고려해 테이블이 있을 때만 raw SQL로 처리.
- **안전장치**: 기본은 `--dry-run`(시뮬레이션), `--apply`에서만 실제 변경. 전체를 `transaction.atomic`으로 감싸 중간 실패 시 롤백.

```bash
python manage.py dedupe_products            # dry-run (변경 없음)
python manage.py dedupe_products --apply     # 적용
```

결과: **156 → 103건**, 중복 0, 임베딩·요약 손실 0.

> **트러블슈팅:** `board.Post.product`(UUID 컬럼)를 raw SQL로 옮길 때
> `operator does not exist: uuid = text` 에러 → 파라미터에 `::uuid` 캐스팅으로 해결.
> (트랜잭션 덕에 데이터는 그대로였고, 고친 뒤 재적용)

## 4. 해결 ② — ai_summary 채우기 (방향 전환이 핵심)

### 첫 시도: 올리브영 재크롤링 → 막힘

`ai_summary`는 사실 **Gemini 생성이 아니라 올리브영 페이지의 자체 'AI 요약'
(`feature-description`)을 긁어온 값**이었다. 그래서 빈 제품을 재방문해 다시
긁는 `refresh_summaries`(셀레니움)를 만들어 3건 테스트했더니:

```
[1/3] 요약없음  AHC 선스틱
[2/3] OK(가격만) 아비브 CC선
[3/3] 요약없음  스킨1004
```

**3건 다 요약을 못 채웠다.** 빈 제품이 죄다 선스틱·CC선·기획세트류였는데,
**올리브영은 이런 제품엔 AI요약을 원래 안 단다.** 재크롤링으로는 못 채운다.

### 전환: 리뷰를 LLM이 요약 — 데이터를 보고 길을 틀다

"올영 요약이 없으면, **리뷰를 읽어서 LLM이 요약**하면 되지 않나?" 가 돌파구였다.
확인해보니 빈 40건은 **리뷰도 0개**였지만(상세 크롤링 중단), 결정적으로:

> 리뷰는 **셀레니움 없이 `requests` API로 가져올 수 있었다.** 테스트 제품은
> 올영에 리뷰가 6,190개나 있었는데 DB엔 0개였을 뿐. → API로 즉시 수집 가능.

그래서 파이프라인을 셋으로 구성했다(**전부 셀레니움 불필요**):

```
① backfill_reviews        리뷰 0개 제품 → 올영 리뷰 API로 수집 (requests)
② summarize_from_reviews  수집된 리뷰 → GMS(LLM)로 1~2문장 요약 → ai_summary
③ backfill_embeddings     채워진 요약 → 임베딩
```

- **②의 요약 품질**: 리뷰 근거로 객관적 특징을 잘 뽑았다. 예) 남성 올인원 →
  *"올인원이라 간편하고 남성용으로 적합. 촉촉하고 흡수 빠름"*. 광고 표현은
  배제하고 리뷰 사실만 담도록 시스템 프롬프트로 제약.
- **GMS 재사용**: 이미 챗봇에 쓰던 `chat.views._call_gms`를 그대로 호출 — 새 인프라 0.

```bash
python manage.py backfill_reviews          # 리뷰 수집
python manage.py summarize_from_reviews    # 리뷰 → 요약
python manage.py backfill_embeddings       # 요약 → 임베딩
```

결과: **ai_summary 63 → 103건(100%)**, 임베딩 100%. RAG 검색 대상이 전 제품으로 확대.

## 5. 해결 ③ — 중복 재발 방지 (`crawling.py`)

원인을 코드에서 끊었다. `run()`을 이렇게 고침:

- 중복 판정을 **URL → `goodsNo` 기준**으로 변경 (파라미터가 달라도 같은 제품은 한 번만)
- 저장을 `Product.objects.create()` → **`get_or_create()`** 로 변경 (멱등)

이후 크롤링을 다시 돌려도 기존 제품은 건드리지 않고 신규만 추가된다.

## 6. 도입한 관리 명령 정리

| 명령 | 역할 | 의존 |
|------|------|------|
| `dedupe_products` | goodsNo 중복 제거 + FK 재연결 (dry-run/--apply) | DB only |
| `backfill_reviews` | 리뷰 0개 제품의 리뷰를 올영 API로 수집 | `requests` |
| `summarize_from_reviews` | 리뷰 기반 GMS 요약 → ai_summary | GMS |
| `refresh_summaries` | 올영 재방문 요약·가격 갱신 | **셀레니움** |
| `backfill_embeddings` | ai_summary → 임베딩 (기존) | GMS |

> `refresh_summaries`는 올영 자체 요약이 있는 제품·가격 갱신용으로 남겨둔다
> (셀레니움 필요). ai_summary 결측은 ①②로 이미 해결됐다.

## 7. 결과

| 지표 | Before | After |
|------|--------|-------|
| 제품 수 | 156 (중복 53) | **103** (중복 0) |
| ai_summary 커버리지 | 63 (61%) | **103 (100%)** |
| 임베딩 커버리지 | 63 | **103 (100%)** |
| RAG 검색 대상 | 63건 | **전 제품** |

`products_seed.json`도 정제본(103건)으로 재생성했다. 단 **임베딩은 seed에서
제외**(파생 데이터라 넣으면 폭증) → `loaddata` 후 `backfill_embeddings`로 복원한다.

## 8. 남은 것 (후속)

- **가격 갱신**: 셀레니움(`refresh_summaries`)이 필요해 별도 작업으로 남김. 가격은
  올영 상세 페이지에서만 정확히 읽혀, 리뷰 API처럼 가볍게는 안 됨.
- **카테고리 편중**: 스킨케어·선케어·클렌징이 96%, 메이크업 4건. 마스크팩·패드는
  0건. 추천 폭을 넓히려면 `crawling.CATEGORIES`에 카테고리(dispCatNo)를 추가하고
  재크롤링하면 된다(`get_or_create` 덕에 기존 103건은 안전).
