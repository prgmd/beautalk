# 추천 실패 분석 보고서 — 제약 조건 미충족

> ⚠️ **시점 주의(2026-06 갱신):** 이 분석은 **103종 시점**(제형 데이터 부재·로션 0건)의 기록이다.
> 이후 ① 하이브리드 추천(SQL 필터+RAG) 도입 ② `form` 필드 구조화·백필 ③ 카테고리 확장 크롤링으로
> **현재 306종**(제형 281종 보유)이 되어, 아래의 구조적 결함은 모두 해소됐다. 본문은 당시 진단 기록.

> 데이터 정제(중복 제거·ai_summary 완비) 이후에도 추천이 **사용자가 명시한
> 제약(제형·가격)을 하나도 충족하지 못한** 사례를 분석한다. 결론부터: 이건
> 데이터 정제로 고쳐지는 문제가 아니라 **추천 구조(아키텍처)의 결함**이다.

---

## 1. 요약

사용자 요청 **"지성 피부, 2~3만원대, 로션/스킨 세트"** 에 대해 추천 결과가:

| 추천 제품 | 제형 | 가격 | 제약 충족 |
|-----------|------|------|:---:|
| 디오디너리 글리코릭 애시드 토너 | **토너** | 16,900원 | ❌ 제형·가격 |
| 더마팩토리 나이아신아마이드 세럼 | **세럼** | 5,700원 | ❌ 제형·가격 |
| 닥터지 레드블레미쉬 수딩크림 | **크림** | 27,600원 | ⚠️ 가격만 |

- **제형**: 로션/스킨을 요청했으나 토너·세럼·크림 → **충족 0/3**
- **가격**: 2~3만원대 요청, 2~3만원대 제품은 DB에 59건 존재했으나 → **충족 1/3**

의미적으로는 "지성·피지·진정" 테마가 일관됐으나, **사용자가 건 제약을 전혀
지키지 못했다.** 추천의 본래 목적(조건에 맞는 제품 제시)에서 실패.

## 2. 진단 — 데이터로 확인한 사실

```
총 제품 = 103건
제품명에 "로션/스킨" 포함 = 4건
  └ 4건마저 실제로는 다른 제형:
     · 스타라이크 "스킨핏 수분 선크림"  → 선크림 (스킨핏=피부 밀착)
     · 우르오스 "스킨밀크/스킨로션"      → 남성 올인원
     · "스킨1004 …선세럼"               → 브랜드명이 스킨1004, 실제 선세럼
2~3만원대(20,000~35,000) = 59건  (가격 후보는 충분)
로션/스킨 AND 2~3만원 = 3건 (그나마 위 가짜 매칭)
```

→ **로션/스킨으로 분류할 제품이 DB에 사실상 0건.** 없는 것은 추천할 수 없다.

## 3. 근본 원인 — 3중 결함

### 원인 1. 제형(category) 부재 — 데이터 결함 🔴

크롤링이 **"스킨케어 / 선케어 / 클렌징 / 메이크업" 대분류로만** 수집해,
**제형(토너·스킨·로션·에센스·세럼·크림) 구분이 없다.** "로션/스킨" 같은
세부 제형으로 거를 수단 자체가 없고, 해당 제품군도 수집되지 않았다.

> 한국 화장품에서 **스킨 = 토너**, **로션 = 에멀전/유액**으로 통용된다.
> 사용자의 "로션/스킨 세트"는 기초 2종(유액+토너)을 뜻하는데, DB에는 이
> 제형 자체가 거의 없다.

### 원인 2. 가격이 프롬프트에 없음 — 로직 결함 🔴

추천 프롬프트 조립부([chat/views.py](../backend/chat/views.py) `_build_recommend_prompt`):

```python
f"id={p.id} | [{p.category}] {p.brand} {p.name}: {p.ai_summary}"
```

**`price`가 포함되지 않는다.** LLM은 후보 제품의 가격을 *볼 수조차 없어서*
"2~3만원대"를 지킬 방법이 없었다. 2~3만원대가 59건 있었음에도 5,700원을 고른
이유가 이것이다.

### 원인 3. 제약을 임베딩에 떠넘김 — 아키텍처 결함 🔴

현재 추천 후보 선정([chat/views.py](../backend/chat/views.py) `_recommend_candidates`)은
**대화 임베딩 → 코사인 유사도 top-N** 이 전부다.

> **임베딩(의미) 검색은 "비슷한 것"을 찾지, "조건을 만족하는 것"을 찾지 않는다.**
> "지성·진정" 같은 의미는 잡아도, **"로션이라는 제형" "2~3만원이라는 범위"
> 같은 정형 제약(structured constraint)은 벡터로 거를 수 없다.**

정형 제약은 SQL 필터(`category`/제형, `price` 범위)로 처리해야 하는데, 현재는
그 필터 단계가 없이 전부 임베딩 하나에 의존한다.

## 4. 핵심 통찰

| 차원 | 적합한 방식 | 현재 |
|------|-------------|------|
| 제형·가격 (정형 제약) | **SQL 필터** (`WHERE`) | 임베딩에 떠넘김 |
| 지성·진정 (의미 유사) | 임베딩 검색 | 임베딩 검색 ✓ |

추천이 제대로 동작하려면 RAG(유사도) **앞에**, 사용자 의도에서 **제형·가격대를
추출해 후보를 SQL로 먼저 거르는 "필터 단계"** 가 있어야 한다. 즉 **하이브리드 검색**
(structured filter + semantic search)이 필요하다.

```
[대화] → 의도 추출(제형·가격대) → SQL 필터(category/제형, price 범위)
                                        │
                                  걸러진 후보 → 임베딩 유사도 정렬 → top-N → LLM
```

## 5. 해결 방향 (우선순위)

| # | 작업 | 성격 | 효과/비용 |
|---|------|------|-----------|
| 1 | **프롬프트에 price 추가** + "가격대 준수" 지시 | 로직 (즉효) | 몇 줄, 가격 충족률 즉시 개선 |
| 2 | **제형 필드 구조화** (제품명 파싱 → 토너/로션/세럼/크림…) | 데이터 | 제형 필터의 전제 |
| 3 | **하이브리드 검색** (제형·가격 SQL 필터 + 임베딩) | 아키텍처 | 근본 해결 |
| 4 | **부족 제형 크롤링 보강** (로션/스킨/에멀전 등) | 데이터 | 후보 풀 자체 확보 |

> 1번은 즉시 적용 가능하나, 2·4(데이터에 제형·제품이 있어야 함)가 받쳐주지
> 않으면 "로션/스킨" 같은 요청은 여전히 충족 불가. **데이터(2·4)와 로직(1·3)을
> 함께** 가야 한다.

## 6. 결론

- 이번 실패는 **데이터 정제(중복·요약)와 무관한 별개의 구조 문제**다.
- 표면 증상(제형·가격 미충족)의 뿌리는 **① 제형 데이터 부재 ② 프롬프트 가격
  누락 ③ 제약을 임베딩에 의존하는 아키텍처** 세 가지다.
- 의미 유사도만으로는 "조건을 만족하는 추천"이 불가능하며, **정형 제약을 거르는
  필터 계층(하이브리드 검색)** 도입이 핵심 과제다.
